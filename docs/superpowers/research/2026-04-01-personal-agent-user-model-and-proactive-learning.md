# Nion 个人助理的用户模型、主动学习与轻量知识渗透研究

## 研究目标

围绕下面这个产品方向做判断与收敛：

- Nion 作为个人全职助理，是否应该持续了解用户的职业、工作节律、兴趣、性格与长期发展方向
- agent 是否应该为了更好服务用户而主动学习对应领域知识
- agent 是否应该在日常沟通中，以不生硬、不说教的方式持续给用户带来一点学习增益

本文不是在讨论“多加一点 memory”。

本文讨论的是：Nion 是否应该从“被动响应助手”，升级为“会持续理解用户、持续补足自己、并在互动中让用户变得更强的个人助理”。

## 已确认事实

下面这些判断，来自 Nion 当前已有设计文档，而不是本文临时假设：

- Nion 的愿景是通用个人办公 AI agent，而不是纯 code agent。
- `Memory`、`Notebook`、`Project`、`Self-Maintenance` 在产品上已经被明确区分，不应再混成一个大杂烩。
- 现有设计已经提出：`AutoDream` 不应继续作为单独产品概念存在，而应被吸收到 `Self-Maintenance` 中，成为 agent 自我维护与反思能力的一部分。
- Nion 当前更需要的是统一 runtime contract，而不是继续往单点功能上打补丁。
- Claude Code 对 Nion 的真正参考价值，主要是 operating model、hooks、permissions、skills、delegation、context hygiene，而不是 code-first 的产品壳。

这些事实意味着：如果要做“越聊越懂你、越服务越专业”的能力，它必须落在 Nion 的通用 runtime 和 memory architecture 上，不能做成一个悬空 gimmick。

## 总判断

这个方向是对的，而且我认为它很可能是 Nion 最有潜力的差异化能力之一。

但它必须被设计成一套**有边界、可治理、可解释、可关闭**的长期用户模型与主动学习系统，而不是“agent 默默观察你、私下成长、顺手教育你”的失控机制。

换句话说：

- 方向本身值得做
- 但不该叫“无限自我进化”
- 更适合被定义为：`Personal Operating Memory + Active Learning + Ambient Teaching`

其中最重要的词是：

- `Personal`：围绕这个具体用户，而不是抽象人群
- `Operating`：服务实际工作流，而不是泛泛陪聊
- `Active Learning`：agent 为了服务质量主动补课
- `Ambient Teaching`：在自然互动里轻量渗透知识，而不是变成老师

## 为什么这件事有价值

### 1. 它让 Nion 真正配得上“个人全职助理”

如果 agent 只记住你的名字、偏好、几个笔记摘要，它更像“有记忆的聊天工具”。

如果 agent 能逐步知道：

- 你是财务主管
- 你每周要给上级写汇报
- 你每月月底要做财务关账与报表
- 你汇报对象更看重风险、结论和异常项
- 你喜欢简洁直给，不喜欢空话

那它才开始具备“助理”属性。

真正高价值的 personal assistant，不是回答问题更快，而是逐步进入用户的工作操作系统。

### 2. 它能把“记忆”升级成“服务能力”

很多 agent 产品把 memory 做成事实仓库：

- 记住用户喜欢什么
- 记住用户做过什么
- 记住一些 profile 字段

这还不够。

更高一级的能力是把记忆转成服务行为：

- 预判你下周可能要写什么
- 预判你汇报时可能缺哪类数据
- 知道什么时候该给模板，什么时候该给结论，什么时候只该给一句提醒
- 在你正准备处理财务事项时，顺手给你一个刚好有用的财务表达或风险判断框架

也就是说，memory 的终局不是“存下来”，而是“服务变强”。

### 3. 它能形成真正的长期用户粘性

对个人 agent 来说，真正难复制的不是 UI，而是：

- 对用户长期工作节律的理解
- 对用户沟通风格的适配
- 对用户成长方向的持续跟随
- 对用户所在专业领域的服务深度

这类积累越久，迁移成本越高，用户越容易把它当成“自己的助理”而不是“一个随时可替换的大模型入口”。

## 这件事应该长成什么，不应该长成什么

### 应该长成的样子

Nion 应该逐步具备四类能力：

1. **用户模型**
2. **工作节律记忆**
3. **面向用户的主动学习**
4. **上下文相关的轻量知识渗透**

### 不应该长成的样子

Nion 不应该变成：

1. 偷偷记录一切的监控型系统
2. 动不动就“教育用户”的说教型系统
3. 一发现用户是某职业，就开始装专家的表演型系统
4. 无边界上网学习、把未经验证内容灌输给用户的高风险系统

核心不是“更主动”，而是“更有分寸”。

## 推荐的产品结构

我建议把这个能力拆成四层。

## 1. User Model Layer

这是 Nion 对“这个人是谁”的结构化理解。

它不应该只是一张 profile 表，而应该至少包含下面几类对象：

- 身份与角色
- 工作领域与职责
- 周期性任务与节律
- 沟通偏好
- 兴趣与放松偏好
- 长期发展目标
- 已验证偏好与高置信度约束

以你举的财务主管为例，Nion 逐步形成的不是一句“用户是财务主管”，而应更像：

- 角色：财务主管
- 高频任务：周报、月度报表、预算对齐、异常项跟踪
- 汇报对象：领导
- 汇报偏好：结论先行、异常突出、避免空洞套话
- 风险敏感点：数据准确性、口径一致、现金流、合规
- 长期目标：管理能力提升、汇报更有说服力、业务理解更强

这里的关键不是字段多，而是这些字段都要能服务实际行为。

## 2. Work Rhythm Memory Layer

这是用户模型里最容易直接产生价值的一层。

Nion 应该记住用户工作中的周期与模式，例如：

- 每周一做周汇报
- 每月月底做财务结账与分析
- 季末做预算复盘
- 年中准备审计材料

这一层比“兴趣标签”更值钱，因为它直接决定 agent 什么时候该主动、主动什么。

如果这层做对了，Nion 的很多主动行为就会非常自然：

- 提前提醒而不是事后补救
- 直接给可编辑初稿而不是泛泛建议
- 知道本周该给你“汇报框架”，月底该给你“报表检查清单”

## 3. Active Learning Layer

这是最有意思、也是最容易做歪的一层。

agent 的主动学习，不应理解成“自由生长”，而应理解成“为了服务当前用户而补足服务所需知识”。

也就是说，学习必须带着明确问题：

- 用户是谁
- 用户在做什么
- 我为什么需要补这块知识
- 学完后会如何提升服务质量

对于财务主管用户，Nion 可以有一条明确的学习议程：

- 补财务分析与管理会计常用框架
- 补领导汇报常见表达与结构化结论方式
- 补财务异常识别、风险表达、口径管理
- 补对该用户所在行业更相关的财务关注点

但这里必须加三道边界：

1. 学习目标必须和用户当前工作或兴趣强相关
2. 学习结果必须带来源、置信度和时效性
3. 学习不能直接越过验证层进入“对用户的确定性建议”

否则 agent 会进入一种非常危险的状态：

- 读了一点网上内容
- 自以为理解了用户行业
- 然后开始输出带权威口吻的错误建议

这在办公场景里风险很高。

## 4. Ambient Teaching Layer

你提到“在聊天中无意识地给用户灌输一些小知识，而且不要很严肃”，我认为这是很好的方向，但表达上最好从“灌输”改成“轻量渗透”。

因为优秀的个人助理不应该像老师，而应该像一个总能在对的时候递来一句刚好有用的话的人。

这一层最好的形态，不是专门开一堂课，而是嵌在任务里：

- 写周报时，顺手给一句“这种场景用‘本周核心进展 / 风险 / 下周动作’会比流水账更适合领导读”
- 做财务分析时，顺手提醒“异常项先说影响，再说原因，最后说处理动作，会更像管理层材料”
- 聊兴趣时，顺手分享一条和用户口味匹配、又不低质的趣闻或行业小知识

这层的原则应该是：

- 轻
- 准
- 顺手
- 不打断主任务
- 用户不喜欢时立刻收敛

## 与 Nion 现有对象层的对齐方式

这件事不能乱塞，必须放进现有对象边界里。

### Memory 里应该放什么

只放 durable、跨场景仍成立的信息：

- 用户职业角色
- 稳定工作节律
- 长期沟通偏好
- 稳定兴趣偏好
- 已验证的发展方向
- 已验证的服务偏好

### Notebook 里应该放什么

放用户明确想沉淀的资料、笔记、研究与草稿，例如：

- “财务汇报表达技巧”收藏
- 某份自己整理的行业分析
- 会议纪要与反思

Notebook 是用户资产，不应被 agent 默认悄悄写入。

### Project 里应该放什么

放项目或阶段性工作的上下文，例如：

- 某次月报专项
- 某次预算复盘项目
- 某次审计准备任务

Project 内部的经验可以先沉淀为 project memory，之后再显式提炼进 global memory。

### Self-Maintenance 里应该放什么

这里正是这类能力最应该落的地方。

Self-Maintenance 可以承担：

- 最近从对话中学到了哪些用户特征
- 哪些判断已足够稳定，值得提炼进 durable memory
- 哪些能力短板值得进入主动学习议程
- 哪些主动分享是有效的，哪些让用户嫌烦
- 哪些兴趣或工作模式判断已经过时，需要衰减或撤销

也就是说，`AutoDream` 最值得保留的，不是名字，而是这种“agent 在后台做有限反思与有限补课”的 skeleton。

## Claude Code / AutoDream 风格中值得借鉴的部分

如果把这件事放进 Nion，我会这样分级：

### S 级：应该直接吸收

- `Self-Maintenance` 驱动的后台反思与整理
- 将学习与反思落入正式 runtime contract，而不是做成神秘后台逻辑
- 对主动行为设置清晰边界、触发条件和可中断性
- 强调 context hygiene，避免把“学到的所有东西”直接塞进主会话

### A 级：很值得做

- 为用户建立结构化 user model，而不是散乱 memory
- 为不同行业建立“服务增强型学习议程”
- 把主动学习结果变成可引用、可验证、可衰减的 knowledge item
- 把“是否继续这样服务”纳入 reflective loop

### B 级：适合后续扩展

- 兴趣相关新闻、趣闻、轻度 serendipity 推荐
- 用户成长陪练，例如逐步提升汇报表达或思考框架
- 根据用户状态切换“今天更像执行助理”还是“今天更像陪练”

### C 级：要谨慎

- 显式“人格进化”
- agent 对自己身份的过强叙事
- 过多拟人化自我表达

### D 级：现在不要做

- 无授权持续联网抓取用户相关信息
- 不透明的高频后台学习
- 未经验证就对用户做专业判断
- 把 agent 训练成“什么都懂一点”的伪专家

## 这件事的核心风险

## 1. 边界感风险

如果 agent 太主动，用户会觉得被观察、被分析、被揣测。

个人助理的理想状态是“懂我”，不是“盯着我”。

## 2. 幻觉型理解风险

对用户的一两次对话样本做过度归纳，非常危险。

例如：

- 用户只是最近刚好在写财务材料
- agent 却把“财务主管”当成稳定身份写死

因此任何 user model 条目都要有：

- 来源
- 置信度
- 最近验证时间
- 可撤销性

## 3. 说教感风险

“顺手给知识”这件事，一旦频率不对，就会很烦。

因此这层要有明确的节流机制：

- 同一任务里最多点到为止
- 用户忽略多次后自动降频
- 用户显式偏好“少教我，多帮我做”时立即收敛

## 4. 专业错误风险

尤其是财务、法务、医疗、投资这类高风险领域。

agent 可以学，但必须知道自己什么时候只是“帮忙整理”，什么时候是在给专业建议。

这意味着：

- 高风险领域的主动学习结果必须附带来源
- 高风险建议默认以“辅助分析 / 草案 / 参考框架”呈现
- 不应伪装成可直接拍板的权威意见

## 5. 产品焦点漂移风险

如果把这件事做成“agent 自我进化秀场”，Nion 会被带偏。

Nion 的目标不是做一个总在展示自我成长的 AI 人格，而是做一个越来越懂用户、越来越能把事办好的个人助理。

## 这件事要成立，必须补的三条产品约束

## 1. 用户授权必须分层，而不是默认全开

这类能力天然带一点“长期观察”属性，所以不能默认黑箱开启。

我建议至少拆成三档：

- 基础记忆：允许记录稳定偏好、工作习惯、周期任务
- 服务增强学习：允许 agent 为了当前工作场景补相关知识
- 轻量主动分享：允许在合适时机分享提示、趣闻、框架或提醒

这样用户可以只开前两层，不开第三层。

也可以只允许“帮我更懂工作”，不允许“顺手给我推荐东西”。

这会直接影响用户对系统边界感的信任。

## 2. 主动学习必须有明确触发器，而不是持续自转

agent 不应该无休止后台学习。

更合理的触发方式应该是事件驱动：

- 某个工作模式被反复观察到
- 某类任务在短周期内高频出现
- 用户明确表达“我想提升这方面能力”
- 当前任务暴露出 agent 的专业短板
- reflective loop 认为某个知识缺口已反复影响服务质量

换句话说，主动学习不是常驻噪声，而是问题驱动的补课机制。

## 3. 学习产物必须先进入知识对象，再决定是否进入 Memory

为了避免“学了一点就写死到用户画像里”，学习结果不应直接写成 durable memory。

更合理的流转是：

1. 先形成带来源的 learning item
2. 再在后续任务里被使用、验证、修正
3. 足够稳定后，再提炼成长期 user model 或 reusable learning

这能避免两类常见错误：

- 把临时观察误当稳定事实
- 把外部资料误当 agent 已掌握真理

## 这套能力在 runtime 里应该挂在哪

如果按 Nion 正在形成的 superpowers runtime 来看，我建议这样落：

## 1. Prompt Runtime：决定这轮对话该以什么身份服务用户

Prompt runtime 不应该只是告诉 agent “你是助理”，还应该注入：

- 当前已验证的用户角色与偏好
- 当前处于什么工作周期
- 本轮允许的主动程度
- 是否允许轻量知识渗透
- 高风险领域的表达边界

也就是说，这件事首先不是 memory feature，而是 prompt runtime 的会话装配问题。

## 2. Tool Runtime Contract：决定主动学习是否被允许、如何被审计

如果 agent 要主动搜资料、读材料、生成学习卡片，这些都属于受治理的工具行为。

因此 tool runtime 里至少要有：

- 主动学习相关工具的分类
- 针对高风险领域的权限或提醒策略
- 来源记录与结果摘要
- 对外部资料的 prompt injection 与可靠性防护

否则“主动学习”只会变成“多调用几次搜索工具”。

## 3. Self-Maintenance：决定学什么、忘什么、什么值得沉淀

这一层最适合承接：

- 用户模型候选更新
- 学习议程生成
- 低价值画像的衰减
- 主动分享效果复盘
- 是否降频或停止某类主动行为

这也是我认为它应该吸收 `AutoDream` 精华的原因。

不是让 agent 在后台做浪漫化做梦，而是让它在后台做**有限、可治理、面向服务质量的反思与补课**。

## 4. Hook Event Plane：决定哪些时机允许轻量主动行为

如果后面 Nion 建立正式 hook event plane，这个能力非常适合挂在下面这些事件附近：

- `UserPromptSubmit`
- `TaskCompleted`
- `SessionEnd`
- `PreCompact`
- `PostCompact`

原因很简单：

- `UserPromptSubmit` 适合判断当前任务是否命中用户长期模式
- `TaskCompleted` 适合记录这次服务有没有暴露知识缺口
- `SessionEnd` 适合生成低打扰的反思候选
- `PreCompact / PostCompact` 适合做记忆提炼与衰减

这会比在主对话里随时乱触发要稳得多。

## 推荐的落地方向

我建议把它分三段做，而不是一次性上全套。

## P0：先把“懂用户”做扎实

先做下面这些：

- 结构化 user model schema
- 周期性工作节律记忆
- memory 写入的来源、置信度、衰减与撤销机制
- reflective loop 中的“用户画像更新建议”
- 对主线程可见但不打扰的“为什么我这么建议你”解释能力

这一阶段先不追求“很会教”，先确保“真的懂你，且懂得靠谱”。

## P1：再做“为了你而学”

在 P0 稳定后，再上：

- 面向用户职业与目标的 learning agenda
- source-backed 学习卡片
- 与具体任务相关的知识补课
- 可控的主动提示与主动草稿生成

这时 agent 的学习应表现为服务质量提升，而不是单独开辟一个“我今天学了什么”的产品舞台。

## P2：最后做“轻量陪练与兴趣增益”

最后再考虑：

- 兴趣向 serendipity 推荐
- 更细腻的轻量知识渗透
- 基于长期目标的成长陪练
- 更明显的个性化陪伴感

这层做早了，容易显得花哨；做晚一点，反而更自然。

## 我对这个方向的结论

我支持这个方向，而且我认为它应该成为 Nion 的核心产品主线之一。

但它不该被包装成一个浪漫化、无限制的 `AutoDream` 神话，而应该被收敛成下面这套产品命题：

> Nion 不是只会记住用户说过什么，而是会逐步理解用户在做什么、将要做什么、想成为什么样的人；为了更好地服务这个用户，它会在边界内主动补课，并在合适的时机把知识、提醒、框架和灵感自然地送到用户面前。

如果把这件事做对，Nion 会从“有长期记忆的 agent”变成“会随着用户一起成长的个人工作搭子”。

如果做歪，它就会变成：

- 监控感很强
- 爱自作聪明
- 喜欢说教
- 偶尔还会一本正经地胡说

所以这件事的关键不在于“主动”，而在于：

- 结构化理解
- 有边界学习
- 低打扰表达
- 可治理的 runtime contract

## 最后一句判断

这不是一个边角增强功能。

如果 Nion 要真正成为个人全职助理，这件事就是主航道能力。

但它的正确形态，不是“更像人”，而是“更懂你，也更会帮你把事情做好”。
