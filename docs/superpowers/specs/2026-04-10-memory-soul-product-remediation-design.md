# Memory / Soul Product Remediation Design

日期：2026-04-10
状态：Draft for review
范围：`C. 产品面修复与桌面体验校正`

## 1. 任务定义

前两个阶段已经完成了两件大事：

1. `Memory / Soul` 的边界与合同已经收口。
2. runtime 主链与兼容层的大部分结构性问题已经被修正。

但这并不等于用户真正得到的是一个“像产品”的系统。最新一轮 dogfood 证明，当前产品面仍然存在两类严重问题：

### 1.1 桌面壳仍然不可靠

Electron 进程可以启动，但窗口没有被正确创建。结果是：

- 桌面端对用户来说仍然可能表现为“启动了但什么都没有”
- 这不是视觉瑕疵，而是 `launch blocker`
- 任何后续产品优化，如果桌面壳本身不稳定，都会被放大成“不可信”

### 1.2 页面已经不是内部控制台，但文案和布局仍然带着内部系统气味

当前 `Memory` 和 `Settings > Soul` 虽然在 IA 上已经回到正确边界，但产品表现仍像“开发者收口后的残留面”：

- 页面里有大量解释系统内部规则的说明性文字
- 有的文案直接在向用户解释“哪些入口已经不存在了”
- 有的文案直接暴露内部状态，如“配置中心当前不可用”
- 空态、统计区、分组命名还存在旧术语和旧心智
- 首页欢迎区仍然偏品牌展示，不够像工作入口

这类问题的共同特征是：**功能可能已经对了，但用户感受到的不是成品，而是一个还在调试中的系统。**

本阶段的目标就是把这一层彻底修掉。

## 2. 设计目标

### 核心目标

- 让桌面端恢复成可稳定打开的第一入口
- 让 `Memory` 从“解释系统怎么工作”改成“安静地展示当前记忆”
- 让 `Soul` 真正成为可发现、可理解、可使用的独立设置模块
- 让首页更像工作入口，而不是品牌欢迎页

### 产品目标

- 普通用户在 `Memory` 中只看到“当前记住了什么”，而不是系统维护说明
- 普通用户在 `Settings > Soul` 中只看到“怎么定义这个助手的长期人格”，而不是内部治理语义
- 设置页不出现内部平台状态和后台系统术语
- 首页进入工作状态的速度更快，视觉重心回到输入与任务开始

### 工程目标

- 用正式合同测试和 UI 文案测试锁住去-debug 化结果
- 用 E2E / dogfood 作为验收，而不是仅靠肉眼猜测
- 修复顺序按依赖推进，避免先抛光页面再发现桌面壳打不开

## 3. 非目标

本阶段不做：

- Memory / Soul 的全新视觉重设计
- Notebook 产品重构
- Automation IA 全量改版
- bridge / daemon / diagnostics center 的完整体验重写
- 新增复杂用户可控能力（例如记忆冻结、记忆手动编辑台、Soul 历史版本浏览）

## 4. 当前证据

dogfood 证据已记录在：

- `artifacts/dogfood/electron-memory-soul-2026-04-10/report.md`

当前确认的问题：

1. Electron 启动后无窗口，属于 P1 桌面阻塞。
2. Memory 页存在明显内部实现式说明文案。
3. Memory 统计区 IA 与三分组产品模型不一致。
4. Settings 弹层暴露“配置中心当前不可用”等内部状态文案。
5. Settings 左侧分类在标准桌面高度下裁切，Soul 可发现性差。
6. 首页欢迎区过重，压缩工作输入区。

## 5. 备选方案

### Option A：只改文案，不改结构

做法：

- 只替换 Memory / Soul / Settings 里的说明性文字
- 不动首页布局
- 不动设置容器高度与导航
- 桌面壳问题单独以后再说

优点：

- 改动最小
- 上手快

缺点：

- 桌面壳 P1 仍然存在
- 设置页的可发现性问题不解决
- 首页仍然不够像工作产品
- 最终还是“换了词，但整体还是半成品感觉”

### Option B：按产品面分批修复

做法：

- 第一批先修桌面壳启动
- 第二批修 Memory 的文案、统计区和空态
- 第三批修 Settings / Soul 的容器、导航和文案
- 第四批压缩首页欢迎区，提升输入优先级
- 每批都用测试和 dogfood 关口收口

优点：

- 风险可控
- 顺序清晰
- 每一批都有可见成果
- 最符合“稳扎稳打”

缺点：

- 需要多轮提交
- 不能一把梭完成所有视觉层问题

### Option C：整体重做 Workspace 外壳

做法：

- 把首页、侧栏、设置、Memory、Soul 一起重做

优点：

- 一次性统一视觉语言

缺点：

- 范围过大
- 会让当前任务从“产品校正”膨胀成“工作台重设计”
- 风险与收益不成比例

### 推荐方案

选择 **Option B**。

原因：

- 它既能解决当前的真实问题，又不会膨胀成整个平台改版
- 能把 `launch blocker`、产品文案、IA、布局这些不同层级的问题拆开
- 最适合配合 TDD 与 dogfood 循环推进

## 6. 修复原则

### 6.1 删除优先

遇到“解释系统机制”的文字，默认先删，不默认改写。

只有当用户完成任务确实需要理解的信息，才保留。

### 6.2 用户看到的是结果，不是内部机制

这些内容不该直接面向普通用户出现：

- 某个入口已经移除
- 某个内部中心不可用
- 稳定层 / 临时层 / 治理元数据这类内部语义
- 系统何时会自动改写什么

这些都应该：

- 由系统自行负责
- 或在用户明确提问时由助手通过对话解释

### 6.3 空态要安静，不要喧宾夺主

空态应该：

- 说明当前没有内容
- 不要把“为空”做成页面主视觉
- 不要额外输出教学式说明

### 6.4 设置页优先解决可发现性，而不是堆叠说明文字

如果 `Soul` 入口已经正确，但用户仍然难以发现或使用，那就是产品没完成。

应优先修：

- 左侧导航高度和滚动
- 分类密度
- 内容区可读性

而不是继续添加说明段落。

### 6.5 首页优先服务“开始工作”

首页欢迎区必须服从一个原则：

- 输入框和任务开始入口优先于品牌展示

欢迎语可以保留，但必须减重。

## 7. 目标产品形态

### 7.1 桌面壳

目标状态：

- Electron 启动后稳定创建窗口
- 窗口直接进入正确 renderer
- runtime profile 失败不会把主窗口变成空白或无窗口

验收结果：

- dev 启动链可稳定拉起窗口
- Electron CDP 可看到实际页面 target，而不是只有 `about:blank`
- 首屏可进入 workspace

### 7.2 Memory 页面

目标状态：

- 页头只保留简洁标题，不保留内部实现说明
- 三个分组卡片只展示内容本身
- 空态文案简洁，不带教学口吻
- 统计区若保留，必须与当前三分组模型完全一致

明确要求：

- 删除“这里只展示已经留下来的……不再包含治理控制台入口”
- 删除“如果有错误，直接在对话里告诉我”等重复规则说明
- 删除“如果这条记错了，直接对我说……”这种逐条教学语句
- `用户上下文 / 历史背景` 改成与正式分组一致，或直接取消这类统计卡

### 7.3 Settings / Soul

目标状态：

- 设置弹层不出现内部平台状态文案
- 左侧导航在标准桌面高度下可稳定访问到 `Soul`
- `Soul` 页面只保留真正用户关心的字段和操作

明确要求：

- 删除“配置中心当前不可用”这类文案在正常产品路径中的直接暴露
- `Soul` 页头删除“这里只保留稳定层……”等内部解释
- `Soul` 页删除“正式入口位于 Settings > Soul”这种自我说明
- `Soul` 页删除“稳定层只响应用户明确设置……”等系统规则说明
- 保留字段：
  - 核心人格
  - 说话方式
  - 价值观 / 边界
  - 关系基调
- 保留动作：
  - 编辑
  - 应用

### 7.4 聊天首页

目标状态：

- 欢迎区压缩
- 输入框和快捷入口上移
- 首页第一感知是“可以立刻开始”，不是“欢迎横幅”

明确要求：

- 减弱大 emoji
- 减少副文案行数和视觉占比
- 不让欢迎区压过输入主区域

## 8. 修复批次

### Batch 1：桌面壳恢复

范围：

- `desktop/src/main/index.ts`
- `desktop/src/main/window.ts`
- `desktop/src/main/daemon-launcher.ts`
- 桌面启动相关测试

目标：

- 修复“Electron 进程存在但无窗口”的问题

验收：

- Electron 可稳定出窗
- 不再只有 `about:blank`
- dogfood 可以直接在 Electron 壳里继续跑

### Batch 2：Memory 去 debug 化

范围：

- `frontend/src/components/workspace/memory/memory-home-page.tsx`
- `frontend/src/components/workspace/memory/memory-summary-cards.tsx`
- 相关合同测试

目标：

- 去掉内部说明文字
- 收口统计区术语
- 调整空态与分组内容层级

验收：

- Memory 页面不再出现内部机制式说明
- 术语只剩正式三分组语义
- 排版更紧凑、信息层级更清楚

### Batch 3：Settings / Soul 产品化

范围：

- `frontend/src/components/workspace/settings/settings-dialog.tsx`
- `frontend/src/components/workspace/settings/soul-settings-page.tsx`
- 必要的 i18n 文案
- 相关合同测试

目标：

- 提升 `Soul` 可发现性
- 删除内部状态与内部规则说明

验收：

- `Soul` 在标准窗口高度下可稳定访问
- `Soul` 页没有调试式解释段落
- 设置页文案更接近正式产品

### Batch 4：首页压缩与首屏优先级校正

范围：

- 欢迎区组件
- 首页布局与间距
- 必要 i18n 文案

目标：

- 让首页输入优先级高于品牌展示

验收：

- 输入区更靠上
- 欢迎区更轻
- 首页更像工作入口

## 9. 测试策略

### 9.1 TDD 策略

每个 batch 都先补 failing test，再改实现。

优先测试类型：

- 合同测试：锁住不该再出现的文案和术语
- 组件测试：锁住布局关键结构
- 桌面测试：锁住窗口创建和启动链

### 9.2 E2E / dogfood 策略

每个 batch 完成后都要回到 dogfood：

- 重新走桌面壳
- 重新检查 Memory
- 重新检查 Settings / Soul
- 重新检查首页

### 9.3 文案审计策略

新增一条显式规则：

- 任何包含“这里只 / 不再 / 当前不可用 / 稳定层 / 临时表达模式 / 治理”这类内部解释语气的产品文案，都要被视为高风险候选项

## 10. 风险与控制

### 风险 1：修文案时只做表层替换，没解决信息层级

控制：

- 不只替换文字，还要同时处理卡片结构和统计区

### 风险 2：修 Soul 时又把内部机制文案换种说法塞回页面

控制：

- 直接删除机制解释，除非有明确用户任务价值

### 风险 3：为了修桌面壳而引入临时兼容分支

控制：

- 优先修启动主链
- 不接受“先加旁路启动 hack，以后再说”

## 11. 结论

本阶段不是“优化一下文案”，而是把已经正确的 Memory / Soul 边界，真正落实成用户可感知的正式产品。

推荐执行顺序：

1. 桌面壳恢复
2. Memory 去 debug 化
3. Settings / Soul 产品化
4. 首页首屏压缩

只有这样，下一轮用户看到的才不是“结构上已经修对，但表面还像调试版”的系统。
