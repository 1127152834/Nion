# Nion 值守模式 / 统一远程入口层产品设计

日期：2026-04-15  
状态：Draft for review  
范围：`Desktop / Daemon / Bridge Channels / Task Model / Permissions / Product Surface`

---

## 1. 设计结论

本设计的结论只有一句话：

> **Nion 不应该把“后台守护进程”作为产品卖点，而应该把它收口成“值守中的个人电脑”。**

对普通用户而言，正确心智不是：

- 我启动了一个 daemon
- 我有若干 bridge bot
- 我可以从某个 IM 工具远程调系统

而是：

- 我的电脑现在在值守
- 窗口关了它也会继续工作
- 我可以从任意已绑定入口联系这台电脑
- 它会替我继续跑任务、收通知、等我确认
- 复杂事情我再回到桌面接管

因此，首版产品形态应采用：

- **方案 C：值守电脑 + 统一远程入口层**

而不是：

- 方案 A：按 channel 各做一套 bot 产品
- 方案 B：把所有入口都退化成一个远程聊天壳

其中：

- 方案 A 会把产品做碎
- 方案 B 虽然容易起步，但会把产品长期做窄
- 方案 C 最符合当前目标场景，也最适合在现有仓库演进

---

## 2. 为什么现在要做这件事

当前仓库里，daemon、desktop bridge、thread runtime、incident 体系都已经开始出现产品化雏形，但它们还主要以工程模块存在，而不是普通用户可理解的产品。

从代码与 README 可以看到，当前系统已经具备以下基础：

- 本地 daemon 运行时
- Electron 启动与 daemon 拉起/复用
- bridge adapter 主链
- task / diagnostics / incidents / channels control-plane surface
- bridge permission resolve 回路
- 定时任务、后台任务和 thread stream 的基础骨架

但这些能力还没有形成统一产品心智。当前风险主要有三类：

1. **后台能力存在，但用户心智不存在**  
   用户仍会把它理解成“窗口没关时才能工作的桌面应用”。

2. **bridge 能力存在，但入口模型不统一**  
   如果继续围绕某个 channel 单独做，会把同一台电脑拆成多个“机器人产品”。

3. **高权限动作边界还不适合直接产品化**  
   当前产品若直接承诺“远程截图/整理文件/控机”，会明显超出普通用户的信任阈值。

所以这轮产品设计不是为了“加更多功能”，而是为了把已经出现的底层能力重新组织成一个普通用户可以理解、可以长期使用的产品。

## 3. 产品定义

### 3.1 产品名称

对外产品名称建议统一为：

- **Nion 值守模式**

内部技术概念仍可保留：

- local daemon
- bridge runtime
- channel adapters
- control plane

但这些不应该直接成为普通用户的产品语言。

### 3.2 产品定义

`Nion 值守模式 = 让一台属于用户自己的个人电脑，在用户不在电脑前时继续在线工作，并允许用户通过任意已绑定的远程入口与这台电脑交互。`

### 3.3 首版边界

首版严格限定为：

- 单个用户
- 一台个人电脑
- 多个已绑定 channel 可同时作为入口
- 不引入团队、组织、共享电脑、多用户审批流

这意味着：

- 用户身份模型是“电脑主人”
- channel 只是进入同一台电脑的不同入口
- 不存在团队成员共同使用同一台电脑的产品语义

### 3.4 首版非目标

首版明确不做：

- 团队协作与多用户
- 群组工作流
- 独立 Web 控制台
- 完整远程桌面
- 任意远程控机
- 任意 shell 直通
- 把每个 channel 做成独立产品

## 4. 北极星场景

本产品首版只围绕三个场景设计。

### 场景 A：后台持续执行

用户离开电脑、关掉窗口后，Nion 仍继续在这台电脑上：

- 跑定时任务
- 维持 bridge/channel 在线
- 继续已有任务
- 汇总结果或异常

核心价值：

- 电脑持续在岗
- 后台任务不依赖前台窗口
- 用户回来时工作已经继续推进

### 场景 B：远程继续交互

用户在外面通过任意已绑定入口联系自己的电脑：

- 问它现在在做什么
- 查看最近结果
- 继续一个已有任务
- 新建一个轻量任务
- 停止一个任务

核心价值：

- 任意入口都能联系同一台电脑
- 入口不同，任务真相相同
- 用户不用记住不同 channel 的产品差异

### 场景 C：需要用户确认

当任务进入敏感或不确定阶段时，Nion 不擅自继续，而是主动发起确认请求：

- 允许一次
- 允许本任务
- 拒绝

核心价值：

- 电脑会继续工作，但不会越界
- 用户在外面也能拍板
- 高风险动作有稳定闭环

## 5. 方案比较与推荐

### 5.1 方案 A：Channel Bot 集合

定义：

- 微信一个产品
- Telegram 一个产品
- 飞书一个产品
- Discord 一个产品

问题：

- 每个 channel 会长出自己的任务语义、确认语义和通知语义
- 长期无法维持一致性
- 工程和产品都会被入口碎片化吞掉

结论：

- 不采用

### 5.2 方案 B：远程聊天壳

定义：

- 所有入口统一成一个“和电脑聊天”的产品

优点：

- 起步快
- 用户容易理解

问题：

- 会把产品长期做窄
- 任务系统、确认系统、值守状态会被消息流掩盖
- 最终像若干 IM bot，而不是一台值守中的电脑

结论：

- 可作为交互外壳
- 不可作为产品定义

### 5.3 方案 C：值守电脑 + 统一远程入口层

定义：

- 产品主体是“我的电脑”
- 多个 channel 只是“进入这台电脑的入口”
- 所有入口共享统一任务与确认系统

优点：

- 最符合当前目标用户
- 可同时容纳 daemon、bridge、定时任务与远程确认
- 长期扩展性最好

代价：

- 首版必须克制，不能急着做入口特化

结论：

- **采用方案 C**

## 6. 核心产品对象

首版产品只保留五个对象。

### 6.1 电脑

电脑是主对象，不是 agent 会话。

用户看到的状态应收口为：

- 未开启值守
- 值守中
- 忙碌中
- 等待我处理
- 异常
- 离线

### 6.2 任务

任务是远程入口层的真相源，不是消息历史。

首版状态收口为：

- `queued`
- `running`
- `waiting_confirmation`
- `waiting_input`
- `completed`
- `failed`
- `cancelled`

### 6.3 远程入口

入口是产品对象，但不是主系统。

每个入口只体现四件事：

- 已绑定 / 未绑定
- 可用 / 异常
- 支持哪些交互能力
- 是否接收通知

### 6.4 确认

确认独立成对象，而不是消息流中的临时按钮。

每个确认请求至少包含：

- 要做什么
- 为什么需要确认
- 风险等级
- 可选动作
- 过期时间
- 属于哪个任务

### 6.5 通知

通知不是附属能力，而是值守模式的重要输出。

首版通知类型收口为：

- 任务开始
- 任务完成
- 任务失败
- 需要确认
- 电脑异常

## 7. 统一远程入口层

### 7.1 统一原则

所有已支持 channel 必须满足：

> **共享同一套能力语义，不共享同一套交互形式。**

也就是：

- 核心能力一致
- 展现形式可不同
- 降级策略清楚
- 任务与确认状态全局一致

### 7.2 Remote Core 10 项能力

所有正式支持的远程入口都必须覆盖：

1. 查看电脑状态
2. 查看当前进行中的任务
3. 查看最近完成/失败的任务
4. 新建一个远程任务
5. 继续一个已有任务
6. 停止当前任务
7. 收到任务完成/失败通知
8. 收到并处理权限确认
9. 收到并回答 clarification
10. 上传附件并让任务使用附件

这里允许交互降级，不允许能力缺失。

### 7.3 Channel 能力分级

为避免“所有入口体验必须完全一样”的错误承诺，首版定义四级能力分层。

#### L1：文本型入口

支持：

- 纯文本发起任务
- 纯文本状态查询
- 纯文本确认/拒绝
- 纯文本 clarification

适合：

- 微信
- QQ
- 其他能力较弱入口

#### L2：交互型入口

支持：

- 按钮
- 快捷操作
- 基础结构化回复

适合：

- Telegram
- Discord
- 部分飞书场景

#### L3：富卡片入口

支持：

- 结构化卡片
- 结果摘要卡
- 状态卡
- richer approval UX

适合：

- 飞书
- 支持 richer UI 的 Telegram/Discord 形态

#### L4：协作型入口

支持：

- 群组
- mention
- 多人交互
- 企业目录

结论：

- 首版不做

### 7.4 首版要求

首版正式支持入口的标准：

- 至少达到 `L1`
- Remote Core 10 项能力全通

优先增强的入口可做到 `L2`。

### 7.5 降级策略

首版必须定义明确降级规则：

- 按钮不可用时，降级为文本命令
- 富卡片不可用时，降级为结构化文本
- 流式更新不可用时，降级为阶段性状态通知
- 复杂结果不适合在入口内消费时，降级为摘要 + 引导回桌面

## 8. 权限模型与安全边界

首版值守模式必须遵循一条总原则：

> **默认把远程入口当作委托工作入口，而不是远程控机入口。**

### 8.1 第一层：自动允许

默认自动执行的低风险动作：

- 查询电脑状态
- 查询任务状态
- 查询最近结果
- 接收通知
- 启动低风险后台任务
- 继续已有低风险任务
- 上传附件
- 停止任务

### 8.2 第二层：显式确认

允许远程发起，但必须先确认的动作：

- 修改任务工作上下文
- 访问更敏感的本地文件
- 触发潜在破坏性文件改动
- 执行高风险命令
- 截图
- 整理文件
- 打开或操作外部应用

确认动作首版只提供：

- 允许一次
- 允许本任务
- 拒绝

首版不提供“永久允许”。

### 8.3 第三层：首版禁用

首版明确禁用：

- 任意系统级桌面控制
- 任意鼠标键盘模拟
- 任意持续屏幕监控
- 任意全盘扫描
- 任意 shell 直通
- 绕过任务系统直接控主机

### 8.4 产品表达

值守模式的对外表达应是：

- Nion 会在后台继续处理你的任务
- 你可以从任意已绑定入口查看和继续这些任务
- 涉及敏感动作时，Nion 会先征求你的确认
- 首版不会开放任意远程控机能力

## 9. 首版版本范围

首版唯一目标是：

> **证明 Nion 值守模式是一个可信的个人电脑后台值守产品。**

### 9.1 Must Have

#### A. 值守成立

- 值守模式开关
- 窗口关闭后继续运行
- 登录后恢复值守
- 后台状态明确可见

#### B. 统一远程入口成立

- 任意已绑定 channel 都进入同一台电脑
- 所有正式支持入口完成 Remote Core
- 入口差异只体现在交互形式

#### C. 任务系统成立

- 查看进行中任务
- 查看最近完成/失败任务
- 新建任务
- 继续任务
- 停止任务
- 收结果通知

#### D. 确认系统成立

- 敏感动作进入显式确认
- 用户可远程批准/拒绝
- 同一确认请求在远程入口和桌面状态一致

#### E. 入口健康可见

- 看到哪些入口已绑定
- 看到入口在线/异常
- 看到最近异常

#### F. 异常时不失控

- 失败任务可见
- 待确认请求不静默丢失
- 入口异常不会伪装成任务完成

### 9.2 Won’t Have

- 多用户
- 团队协作
- 独立 Web 控制台
- 高权限本机动作开放
- 任意远程控机
- channel 深度特化优先

## 10. 里程碑建议

### 里程碑 1：值守基础可信

目标：

- 用户关掉窗口后，Nion 仍然值守

交付：

- 值守开关
- 后台继续运行
- 后台状态页
- daemon / bridge 基础生命周期稳定

### 里程碑 2：远程入口闭环可信

目标：

- 任意已绑定入口都能完成 Remote Core

交付：

- 统一任务状态
- 统一结果回收
- 统一继续/停止/查看状态
- 入口能力降级策略

### 里程碑 3：确认与异常可信

目标：

- 用户在外面也能放心把电脑交给它

交付：

- 确认系统
- clarification 系统
- 失败通知
- 入口异常提示
- 待处理中心

## 11. 成功指标

首版不应只看 DAU，而应看值守是否成立。

### 11.1 值守指标

- 值守开启率
- 值守开启后 7 日保持开启率
- 窗口关闭后后台连续运行成功率
- 后台恢复成功率

### 11.2 远程入口指标

- 已绑定入口正式可用率
- 任意入口 Remote Core 覆盖率
- 远程任务启动成功率
- 远程任务完成率

### 11.3 任务指标

- 后台任务成功率
- 停止任务成功率
- 任务结果通知送达率
- 失败任务可见率

### 11.4 确认指标

- 确认请求送达率
- 确认响应率
- 确认后任务恢复成功率
- 误触发敏感确认率

### 11.5 信任指标

- 用户对“它还在工作”的认知清晰度
- 用户对“它会先问我再做敏感动作”的信任感
- 因状态不可见产生的困惑反馈数量
- 因权限边界不清产生的负反馈数量

### 11.6 北极星指标

建议首版北极星指标定义为：

> **窗口关闭状态下，用户通过任意已绑定入口成功完成远程任务的周活跃占比。**

## 12. 当前实现约束与产品影响

本节记录当前仓库现实，以避免产品文档脱离落地条件。

### 12.1 当前已具备的基础

当前仓库已具备：

- 本地 daemon 运行时
- Electron 拉起或复用 daemon
- bridge adapters 主链
- thread stream 接入
- permission resolve 回路
- channels / diagnostics / incidents / runtime-info control plane

这些基础说明值守模式不是从零开始，而是在已有底层能力之上重新收口产品。

### 12.2 当前必须尽快修正的三处缺口

#### 缺口 A：bridge 生命周期仍依赖 desktop 主进程

当前 bridge owner 仍在 Electron main 侧，而不是彻底 daemon-owned。  
这意味着“窗口关了还能值守”在产品上成立，但“桌面主进程退出后 bridge 仍独立存活”还不是稳定合同。

产品影响：

- 值守模式可信度受限
- “后台还在”与“远程入口还在”存在潜在错位

#### 缺口 B：surface policy 与 bridge surface 未对齐

当前配置与运行时中，`channel` 与 `bridge` 的 surface 命名存在边界错位。

产品影响：

- 首版无法稳定宣称远程入口的权限边界已被系统性收口

#### 缺口 C：远程工作目录语义尚未真正进入执行上下文

当前 `/cwd` 等入口语义仍更多停留在 binding 层，而非真实执行上下文合同。

产品影响：

- 首版不能对外承诺“远程入口可稳定切换和继承本地工作目录语义”

### 12.3 当前产品约束

因此，首版 PRD 必须遵循：

- 先卖“值守中的电脑”
- 不卖“完整远程控机”
- 不把高级本机动作写进首版主承诺

## 13. 参考产品启发

本设计吸收以下产品方法，但不照搬其实现边界。

### Cursor Background Agents

吸收点：

- 异步任务而不是同步会话中心
- 跨端 handoff
- 任务状态优先于消息壳

不照搬：

- 远程 worker 环境模式

### Tailscale

吸收点：

- 高权限后台服务与前台 UI 分离
- 服务可长期运行，界面只是管理入口

不照搬：

- 网络设备管理产品心智

### Syncthing

吸收点：

- 后台 invisibly running
- 用户看的是明确状态，而不是内部实现

不照搬：

- 以本地 Web GUI 为主控制面

### Claude Code

吸收点：

- 高能力系统必须靠权限边界建立信任

不照搬：

- 面向开发者的权限术语和交互复杂度

---

## 14. 开放问题

这些问题不阻塞首版设计成立，但会影响后续阶段优先级。

1. 首版正式支持的 channel 名单要收得多窄  
   建议按“Remote Core 全通”为标准，而不是按现有 adapter 数量硬上。

2. 首版值守模式是否需要 menubar / tray 入口  
   建议需要，但不阻塞 PRD 主体成立。

3. 高权限本机动作何时进入下一阶段  
   建议在值守与统一远程入口稳定后，再单独立项为“受控本机动作”。

4. 后续是否增加轻量控制台  
   当前明确不是首版必需项，但中期可能成为效率提升项。

---

## 15. 最终判断

Nion 这条线的正确方向不是：

- 做一个更强的后台 daemon
- 做一组分散的 bridge 机器人
- 做一个能远程控机的技术演示

而是：

> **做一个普通用户愿意长期开启的、持续在线的个人电脑值守层。**

它的第一价值不是万能，而是：

- 可靠
- 清楚
- 可控
- 可从任何入口联系
