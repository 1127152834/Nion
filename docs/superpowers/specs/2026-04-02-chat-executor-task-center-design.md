# Chat 内执行器任务中心设计

## 背景

Nion 当前已经具备聊天线程、项目线程、工具活动时间线、运行时配置、桥接状态、模型选择器和输入框 mention 体系，但还没有把外部代码执行器稳定地纳入聊天主流程。

当前“Agent 集成”页更接近 ACP 适配器配置壳层：

- 偏工程师视角
- 偏静态配置
- 不能直接支撑聊天内派任务
- 不能自然支撑持续会话
- 不能自然支撑同一线程内多个 Codex / Claude Code 并行工作

这导致一个根本问题：

用户知道 Codex / Claude Code 很强，但在 Nion 里不知道该如何自然地“点名派活、持续追问、观察过程、接收结果、并行协作”。

本设计要解决的不是“设置页怎么更友好”，而是把 Codex / Claude Code 完整纳入 Nion 的聊天工作流。

## 外部调研结论

本轮参考了三类公开项目：

- [anthropics/claude-code](https://github.com/anthropics/claude-code)
- [coder/agentapi](https://github.com/coder/agentapi)
- [winfunc/opcode](https://github.com/winfunc/opcode)
- [milisp/codexia](https://github.com/milisp/codexia)

调研结论一致指向一个方向：

1. 成熟产品不会把 Claude Code / Codex 简单当成“普通模型”
2. 更合理的做法是把它们视为外部执行器或外部会话
3. 真正有价值的不是一个开关，而是：
   - 如何派任务
   - 如何持续复用同一个执行上下文
   - 如何观察过程
   - 如何做审批
   - 如何在一个主线程里并行调度多个外部会话

因此，Nion 不应把 Codex / Claude Code 设计成模型列表中的普通模型项，也不应只是一个一次性工具调用；它们应被纳入 Nion 的聊天内执行器任务中心。

## 目标

把 Codex / Claude Code 作为聊天内可点名调用、可持续追问、可并行协作的外部执行器纳入 Nion。

用户目标态应当是：

- 在主聊天里输入 `@codex` 或 `@claude`
- 把某个任务明确交给外部执行器处理
- 在同一个聊天中继续追问同一个执行器会话
- 同时运行多个执行器会话
- 在底部控制台看到真实执行过程
- 在聊天里收到结构化结果，而不是一大坨 CLI 文本
- 复杂度留在后台，前台交互保持极简

## 非目标

本设计不做下列事情：

- 不把 Codex / Claude Code 当成普通模型项塞进模型列表
- 不把前台做成一个专业调度控制台
- 不让用户显式理解 ACP、runner、adapter、PTY、session restore 等内部术语
- 不把聊天线程永久绑定到某一个外部执行器

## 设计原则

### 1. Nion 是主控，外部执行器不是主聊天

用户始终在和 Nion 聊天。Codex / Claude Code 只是被 Nion 调度的外部执行器。

### 2. 前台极简，复杂度全部沉到后台

前台只保留必要入口：

- `@` 面板
- 聊天内任务卡
- 底部可收起控制台

其余复杂机制全部隐藏。

### 3. 线程不绑定执行器，任务才绑定执行器

一个 Nion 线程里可以同时存在多个外部执行器会话。线程属于 Nion，不属于 Codex 或 Claude Code。

### 4. 持续会话优先，不做一次性调用

用户可以持续追问同一个 Codex / Claude Code 会话，而不是每次都新开一条 CLI 进程上下文。

### 5. 写任务默认隔离

写型执行器会话默认运行在独立 worktree 和 branch 中，除非用户显式要求直接操作当前工作区。

### 6. 结果回流聊天，过程留在控制台

聊天里显示任务卡和归纳结果；原始执行过程放到底部控制台中，不污染主消息流。

## 方案比较

### 方案 A：模型级集成

把 Codex / Claude Code 作为模型列表里的可选项。

优点：

- UI 改动看起来最少

缺点：

- 从概念上混淆“模型”和“外部执行器”
- 不自然支持持续 CLI 会话
- 不自然支持一个线程内多个 Codex / Claude 会话并行
- 容易把审批、日志、worktree、任务状态全部塞进模型逻辑中

结论：不采用。

### 方案 B：一次性工具调用

把 `@codex` / `@claude` 视为一次性工具调用，任务跑完即结束。

优点：

- 实现相对直接
- 用户心智容易理解

缺点：

- 很难自然支持“继续在同一个 Codex 里追问”
- 很难自然支持多会话并行
- 运行过程、任务状态、失败恢复、审批很快会变成补丁

结论：不采用。

### 方案 C：聊天内执行器任务中心

Nion 维持主聊天线程，Codex / Claude Code 作为外部执行器会话被创建、复用、调度、观察和回收。

优点：

- 符合用户“点名派活”的直觉
- 能自然支持持续会话
- 能自然支持多个 Codex / Claude 并行
- 能把复杂度留在后台而不污染前台
- 与现有 thread / project / activity timeline 架构兼容

结论：采用。

## 核心结论

Nion 中的 Codex / Claude Code 不是模型，也不是一次性工具，而是聊天内的外部执行器会话。

用户交互只需要理解三件事：

1. 在聊天里用 `@` 选择对象
2. 任务卡展示结果和后续动作
3. 底部控制台展示真实执行过程

## 前台产品形态

### 1. `@` 面板是统一入口

`@` 继续作为统一对象入口，但不再只服务上下文和 notebook。

弹出面板顶部增加三个 tab：

- `上下文`
- `牛马棚`
- `执行器`

其中：

- `上下文` 负责文件、目录、项目上下文
- `牛马棚` 负责 notebook / 牛马棚条目
- `执行器` 负责 Codex、Claude Code 和已有执行器会话

前台不出现 `ACP` 术语。`ACP` 只作为后台实现细节存在。

### 2. `@` 面板交互规则

- 默认打开上次使用的 tab
- `Tab` 在 tab 间切换
- 搜索框在当前 tab 内过滤
- `ArrowUp` / `ArrowDown` 导航
- `Enter` 选择
- `Esc` 关闭

### 3. `执行器` tab 内容

`执行器` tab 只显示两组对象：

- 新建执行器会话
  - `Codex`
  - `Claude Code`
- 继续已有会话
  - 最近会话别名
  - 例如 `登录页修复`
  - 例如 `测试补齐`
  - 例如 `后端重构`

插入形式统一为：

- `@Codex `
- `@Claude Code `
- `@登录页修复 `

前台文本不暴露内部类型前缀。

### 4. 聊天页保持极简

聊天页只新增两类可感知元素：

#### 4.1 任务卡

外部执行器任务在聊天流中以任务卡呈现。

任务卡只显示：

- 执行器名称
- 会话别名
- 当前状态
- 最近一句进展
- 主要产出摘要

默认主按钮只有：

- `继续`
- `控制台`
- `查看改动`
- `停止`

其余管理动作进入二级菜单，不增加主界面负担。

#### 4.2 底部控制台抽屉

聊天页底部增加一个可收起控制台抽屉。

默认收起时仅显示轻量状态条，例如：

- `Codex 正在执行 2 个任务`
- `1 个任务等待你的批准`

展开后表现为多会话 tab 控制台：

- 每个外部执行器会话一个 tab
- 每个 tab 显示名称、执行器类型、状态、未读事件数

每个会话 tab 下提供四个子视图：

- `进展`
- `日志`
- `改动`
- `审批`

默认打开 `进展` 而非 `日志`，避免普通用户被原始终端噪声淹没。

### 5. 用户真实心智

前台最终要让用户只理解以下一句话：

`我在和 Nion 聊天；我可以用 @Codex / @Claude 派任务；它们的过程在底部看；结果回到聊天里；我还能继续追问任何一个会话。`

## 核心对象模型

### 1. Thread

Nion 主聊天线程。

职责：

- 容纳用户对话
- 容纳任务卡和结果消息
- 容纳外部执行器事件摘要
- 作为所有外部执行器会话的父上下文

### 2. Executor Session

外部执行器持续会话。

每个会话至少具备：

- `session_id`
- `thread_id`
- `project_id`
- `agent_kind`
- `display_name`
- `repo_path`
- `worktree_path`
- `branch_name`
- `mode`
- `status`
- `adapter_kind`
- `adapter_session_id`
- `summary`
- `last_activity_at`

职责：

- 承载持续上下文
- 允许多轮继续追问
- 绑定工作目录和执行权限
- 作为底部控制台的最小观察单位

### 3. Executor Turn

发给某个会话的一次具体任务。

每个 turn 至少具备：

- `turn_id`
- `session_id`
- `thread_id`
- `user_message_id`
- `raw_command`
- `parsed_intent`
- `requirements`
- `acceptance_criteria`
- `write_scope`
- `status`
- `result_summary`
- `result_payload`

职责：

- 作为一次明确工作请求的审计单位
- 作为审批和失败恢复的边界
- 作为任务卡结果生成的直接输入

### 4. Executor Event

执行器事件流统一模型。

至少包含：

- `event_id`
- `session_id`
- `turn_id`
- `event_type`
- `level`
- `summary`
- `payload`
- `created_at`

职责：

- 驱动控制台 `进展`
- 驱动线程级 activity timeline
- 驱动项目 timeline
- 驱动失败恢复和审批展示

### 5. Executor Approval

待批准动作统一模型。

至少包含：

- `approval_id`
- `session_id`
- `turn_id`
- `scope`
- `reason`
- `requested_action`
- `allowed_options`
- `status`

## 会话与任务规则

### 1. 会话和任务的关系

- 一个线程可以有多个会话
- 一个会话可以有多个 turn
- 一个 turn 只属于一个会话
- 同一个会话内的 turn 串行执行
- 不同会话之间可并行执行

### 2. 会话继续规则

继续同一个执行器工作的主入口有两个：

- 任务卡上的 `继续`
- 输入框中的 `@会话别名`

两者底层都解析到同一个 `session_id`。

### 3. `@` 解析规则

#### `@Codex`

表示将本次任务派给 Codex。

系统按以下顺序决定复用还是新建：

- 同线程
- 同项目 / 同仓库
- 同执行器类型
- `idle` 会话优先
- `mode` 匹配优先
- 最近活跃优先

如果候选不唯一，弹出轻量选择器，不自动猜。

#### `@Claude Code`

规则同上，只是执行器类型换成 Claude Code。

#### `@会话别名`

直接命中某个已有会话。

### 4. 强制新建规则

以下情况必须新建会话：

- 用户使用显式新建动作
- 目标仓库不同
- 旧会话不可恢复
- 用户明确要求新开一条工作线
- 旧会话已归档

## 执行模式与隔离策略

### 1. 读模式

读模式会话用于：

- 调研
- 代码阅读
- 诊断
- 审查

特点：

- 默认可共享当前仓库视图
- 不要求独立 worktree

### 2. 写模式

写模式会话用于：

- 改代码
- 重构
- 补测试
- 生成文件

默认规则：

- 自动创建独立 worktree
- 自动绑定独立 branch
- 后续继续追问都在该 worktree 和 branch 上推进

这是本设计的硬规则，而不是可选建议。

### 3. 并行规则

- 不同读会话可并行
- 读会话与写会话可并行
- 不同写会话可并行，但前提是 write scope 不冲突
- 同一会话内不允许并行 turn

## 权限与审批模型

Nion 必须是审批中枢，外部执行器不能绕过 Nion 自己做最终高风险授权。

### 权限分层

#### 1. 安全读取

例如：

- 读文件
- 搜代码
- 列目录
- git status

默认可自动放行。

#### 2. 受控执行

例如：

- 跑测试
- 格式化
- 安装依赖
- 访问网络

可按会话策略决定：

- 本次允许
- 本会话允许
- 拒绝

#### 3. 写入修改

例如：

- 编辑文件
- 创建 worktree
- 写入新文件
- 生成 patch

写型会话默认允许在声明范围内工作，但越界写入需要再次审批。

#### 4. 高风险动作

例如：

- 删除大量文件
- reset / checkout 覆盖
- push 远程
- 执行危险 shell

必须强审批。

### 审批卡展示

审批卡应展示：

- 谁请求的
- 在哪个会话
- 请求做什么
- 为什么需要这样做
- 影响范围
- 可选操作

前台只提供有限明确按钮：

- `仅这次允许`
- `本会话允许`
- `拒绝`

## 结果回流规则

外部执行器的原始输出不能直接作为最终聊天答复。

系统必须把执行结果归一成三层输出：

### 1. 聊天结果

在聊天流中回写一张结果卡和一段归纳消息，说明：

- 做了什么
- 改了哪些文件
- 测试情况
- 是否需要你继续决策

### 2. 控制台过程

完整 CLI 过程进入底部控制台：

- `进展`
- `日志`
- `改动`
- `审批`

### 3. 时间线摘要

线程级和项目级时间线只保留摘要，不堆原始日志。

## 失败恢复

失败被统一分成四类：

### 1. 前置失败

例如：

- 未安装
- 未登录
- 仓库不存在
- worktree 创建失败

表现：

- 不直接向用户抛原始错误栈
- 直接给出修复动作

### 2. 运行失败

例如：

- CLI 崩溃
- adapter 断开
- 会话丢失

恢复动作：

- `重试此任务`
- `重连会话`
- `新开会话继续`

### 3. 业务失败

例如：

- 理解错需求
- 改错文件
- 测试没过

结果卡必须明确：

- 已完成部分
- 未完成部分
- 建议下一步

### 4. 权限阻塞

例如：

- 审批未处理
- 用户拒绝高风险操作

表现：

- turn 进入 `blocked`
- 会话保持可继续

## 设置页与首次引导

“Agent 集成”页不再作为主要使用入口，而是转型为执行器注册与健康中心。

主要职责变为：

- 检测是否已安装
- 检测是否可执行
- 检测是否已登录
- 检测是否健康
- 设置默认工作目录
- 设置默认权限策略
- 展示最近探测结果

真正使用入口回到聊天输入框。

### 首次使用流程

当用户第一次在聊天里选择 `Codex` 或 `Claude Code` 时：

1. 检测是否已安装
2. 检测是否能运行
3. 检测是否已登录
4. 要求选择或确认工作目录
5. 明确告知写任务默认运行在独立 worktree

引导结束后自动恢复原始消息执行，不要求用户重新输入。

## 项目集成

如果当前线程属于某个项目线程：

- 执行器会话同时挂到 thread 和 project
- 关键事件写入 project timeline
- worktree / branch 信息可在项目侧查看
- 任务结果可关联到 artifact 和后续计划

但执行器会话不是 project 的替代品。

它只是 project 内的一种执行资源。

## 后台运行时设计

虽然前台必须极简，但后台需要完整建模。

### 1. 统一编排器

新增 `ExternalExecutorOrchestrator`，负责：

- preflight
- 会话解析
- turn 派发
- 事件归一化
- 结果回流
- 审批与失败恢复

### 2. 执行器运行接口

统一 runner 接口至少需要：

- `probe`
- `create_session`
- `resume_session`
- `submit_turn`
- `interrupt_turn`
- `stop_session`
- `stream_events`
- `collect_artifacts`

### 3. 执行器实现

首批实现：

- `CodexRunner`
- `ClaudeCodeRunner`

每个 runner 内部可使用：

- ACP adapter
- 或 PTY / CLI adapter

但这些都是实现细节，不能泄漏到前台心智中。

## 与现有 Nion 架构的关系

本设计不是另起炉灶，而是挂接到现有 Nion 结构上：

- 线程仍然使用现有 thread 流
- 项目线程仍然使用现有 project 流
- activity timeline 继续复用现有方向
- 输入框 mention 体系继续复用现有 `@` 入口
- 运行时 profile、working directory、artifact、project context 都继续使用现有能力

新增的是“外部执行器任务中心”这一层产品 contract。

## 完整目标态验收标准

只有当下面这些能力全部成立，才算设计达成目标态：

1. 用户可以在聊天里通过 `@` 面板切到 `执行器` tab 并选择 `Codex` 或 `Claude Code`
2. 用户可以在聊天中继续选择某个已有会话别名
3. 同一个会话可以被持续追问
4. 同一个线程可以并行存在多个外部执行器会话
5. 写型会话默认在独立 worktree 中运行
6. 聊天流里能看到任务卡和结构化结果
7. 底部可收起控制台能看到多会话执行过程
8. 高风险动作经过 Nion 审批
9. 失败任务有明确恢复动作
10. 项目线程中能看到执行器任务摘要和结果挂接

## 测试策略

### 1. 输入与引用测试

- `@` 面板 tab 切换
- `执行器` tab 检索与选择
- `@Codex`、`@Claude Code`、`@会话别名` 元数据正确写入

### 2. 会话管理测试

- 新建会话
- 复用会话
- 同线程多会话并行
- 会话别名继续追问

### 3. 权限测试

- 读操作自动放行
- 写操作受控
- 高风险动作强审批
- 拒绝后 turn 进入 blocked

### 4. worktree 测试

- 写型会话自动创建独立 worktree
- 同 worktree 持续追问不丢上下文
- 多写会话并行时冲突检测生效

### 5. 结果回流测试

- 任务卡状态变化
- 控制台事件流更新
- 聊天归纳消息生成
- project timeline 摘要写入

### 6. 恢复测试

- CLI 崩溃
- adapter 断线
- preflight 失败
- 审批阻塞

## 最终结论

Nion 应把 Codex / Claude Code 设计成聊天内可持续调用的外部执行器任务中心，而不是模型，也不是一次性工具。

前台必须保持简单：

- `@` 面板
- 任务卡
- 底部控制台

后台则完整承担：

- 会话管理
- 任务调度
- 过程采集
- 权限审批
- worktree 隔离
- 结果归一

这样既能满足“完整功能”，又不会把聊天页做成一个复杂的工程师控制台。
