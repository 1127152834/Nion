# Automation Advanced Features Design

## Goal

为 Nion 自动化模块定义一套清晰的“默认区 / 高级区”能力边界，解决当前自动化页里“高级选项名不副实、调度能力表达不足、任务配置无法覆盖真实场景”的问题。

本文档只定义高级功能分层与产品设计，不直接包含实现计划，也不改变现有 API 作为上线前提。

## Current Problem

当前自动化模块存在三个核心问题：

1. 调度表达过浅。
   现有创建表单主要暴露“每天 / 工作日 / 每周 + 时间”，无法覆盖单次日期提醒、每月提醒、相对时间提醒等高频真实场景。
2. 高级选项范围过窄。
   当前“高级选项”基本只包含 `delivery_mode` 和 `skills`，无法支撑复杂任务配置，也无法让用户理解为什么需要展开高级区。
3. 配置结构偏工程视角。
   用户真正关心的是“什么时候触发、触发后做什么、结果送到哪里、失败了怎么办”，而不是一堆离散字段。

## Product Decision

自动化模块中的高级功能不应理解为“更难的设置”，而应理解为：

- 普通用户默认不必配置
- 复杂场景下可以把任务设准、送准、跑稳
- 进入高级区后，用户看到的是成组能力，而不是孤立字段

因此，高级功能按四个能力组组织：

1. 调度高级功能
2. 执行高级功能
3. 投递高级功能
4. 治理高级功能

## Default vs Advanced Boundary

### 默认区应保留的最小配置

默认区只回答三个问题：

1. 做什么
2. 什么时候做
3. 结果怎么提醒我 / 交付给我

默认区推荐字段：

- `name`
- `prompt`
- `trigger_mode`
  - 单次
  - 每天
  - 工作日
  - 每周
- `time_or_datetime`
- `delivery_surface`
  - 本地提醒
  - 发送到线程

### 高级区才展开的配置

高级区只在以下情况展开：

- 用户选择“自定义”
- 用户需要非基础调度规则
- 用户需要多通道投递
- 用户需要附加技能、审批、失败策略或团队能力

高级区不应默认展开，也不应把简单任务强行拉进复杂配置流。

## Advanced Features Table

| 功能组 | 功能名 | 解决什么问题 | 适合谁 | 默认区 / 高级区 | 建议产品表达 | 建议数据结构 |
|---|---|---|---|---|---|---|
| 调度 | 单次日期提醒 | 解决“像日程提醒一样按具体日期时间触发” | 所有用户 | 默认区 | 日期时间选择器 | `schedule_kind=once`，`schedule_metadata.run_at` |
| 调度 | 相对时间提醒 | 解决“事件前后提醒”，如会议前 30 分钟 | 重度提醒用户 | 高级区 | “在目标时间前/后 X 分钟” | `schedule_metadata.offset_minutes`，`anchor_time` |
| 调度 | 自定义重复规则 | 解决“每月 1 号 / 每周一三五 / 每 2 小时” | 高级用户 | 高级区 | 调度编辑器 | `schedule_kind=cron|interval`，`schedule_metadata` 存结构化规则 |
| 调度 | 周期跳过 / 本次稍后 | 解决“不改规则，只处理本次提醒” | 所有用户 | 列表快捷操作 | “跳过本次”“10 分钟后再提醒” | 单次 override 记录，不改原 job |
| 调度 | 生效时间窗 | 解决“只在工作时间、只在本周有效” | 高级用户 | 高级区 | 有效期和时间窗 | `schedule_metadata.active_window` |
| 执行 | 附加技能 | 解决“任务运行时需要特定能力” | 高级用户 | 高级区 | 技能选择器 | `skills[]` |
| 执行 | 动作类型切换 | 解决“提醒 / 播放声音 / 写 Notebook / 跑提示词”差异 | 中高级用户 | 默认区 + 高级补充 | 动作卡片选择 | `action_kind`，`action_spec` |
| 执行 | 执行前预览 | 解决“用户不知道这次会实际做什么” | 所有用户 | 默认区 | 结果预览卡 | 前端派生视图，无需新字段 |
| 执行 | 手动试跑 | 解决“上线前先验证自动化逻辑” | 中高级用户 | 高级区 | “测试一次” | 复用 `run job now` |
| 执行 | 失败重试策略 | 解决偶发失败后完全丢失执行机会 | 高级用户 | 高级区 | 重试次数 / 间隔 | `retry_policy` |
| 投递 | 单通道投递 | 解决“只提醒我本人” | 所有用户 | 默认区 | 本地 / 线程二选一 | `delivery_mode` |
| 投递 | 多通道投递 | 解决“同时发本地通知、线程、频道” | 高级用户 | 高级区 | 多选目标面板 | `delivery_mode=multi`，`delivery_targets[]` |
| 投递 | 条件投递 | 解决“只有失败才通知频道，成功只本地提示” | 高级用户 | 高级区 | 按结果配置投递 | `delivery_targets[].when` |
| 投递 | 失败回退通道 | 解决主通道失败后消息丢失 | 高级用户 | 高级区 | 兜底通知设置 | `fallback_delivery` |
| 治理 | 审批策略 | 解决高风险动作自动执行不可控 | 团队 / 高风险场景 | 高级区 | “执行前需批准” | `approval_policy` |
| 治理 | 可见范围 | 解决个人任务与团队任务混杂 | 团队用户 | 高级区 | 仅自己 / 共享 / 团队 | `visibility` |
| 治理 | 连续失败保护 | 解决任务反复失败刷屏或反复执行 | 所有高级用户 | 高级区 | “连续失败 N 次后暂停” | `guardrail_policy` |
| 治理 | 审计与恢复 | 解决“为什么失败、怎么恢复、谁改过” | 团队 / 管理者 | 列表详情与历史页 | 历史、审计、恢复入口 | 复用 runs + audit，必要时扩展 |

## Recommended UI Grouping

### 默认创建流

默认创建流推荐按四步组织：

1. `任务类型`
   - 提醒我
   - 自动执行任务
   - 事件触发
2. `触发时间`
   - 今天
   - 明天
   - 每天
   - 工作日
   - 每周
   - 自定义
3. `执行动作`
   - 通知我
   - 运行提示词
   - 写入 Notebook
   - 播放声音
4. `确认预览`
   - 用自然语言展示最终规则

### 高级区分组

高级区应按分组折叠，不应把全部字段平铺在一个面板里：

- `高级调度`
- `高级执行`
- `高级投递`
- `治理与安全`

每组下方都需要一句解释文案，告诉用户“什么时候才需要它”。

## Detailed Guidance Per Group

### 1. 调度高级功能

这是当前最应该优先补强的部分。

原因：

- 用户最容易先感知“时间设不准”
- 当前系统底层已经具备 `once / interval / cron / event` 能力
- 只补 `delivery_mode` 和 `skills` 无法提升创建体验

设计要求：

- 单次提醒必须成为一等能力，而不是高级能力
- 自定义调度必须输出“自然语言预览”
- 不允许把 cron 表达式直接暴露给普通用户

### 2. 执行高级功能

这组能力回答的是“触发以后到底做什么”。

设计要求：

- 用户先选动作类型，再出现该动作对应的高级配置
- `skills` 不应只是裸文本输入，应该升级为可检索、可解释的技能选择器
- “测试一次”必须在复杂规则中可见，否则用户会担心自动化失控

### 3. 投递高级功能

这组能力回答的是“结果送到哪里、什么情况下送”。

设计要求：

- 默认区只保留最常见的 1 到 2 个投递面
- 多通道、条件投递、失败回退统一归入高级投递
- 投递配置应以“接收方”为中心，而不是底层通道字段为中心

### 4. 治理高级功能

这组能力不该抢占主流程，但对团队场景和高风险任务是必要能力。

设计要求：

- 治理能力不进入默认创建流
- 审批、可见范围、连续失败暂停等能力应只在需要时出现
- 审计与恢复更适合放在详情页和历史页，而不是创建表单

## Information Architecture Recommendation

自动化模块中与“高级功能”强相关的页面结构建议如下：

```text
Automation
├── 概览
├── 全部自动化
├── 创建自动化
├── 执行记录
└── 事件中心
```

不建议继续以大量横向 tab 承载越来越多子产品，否则：

- 新用户不知道从哪里开始
- reminder / task / event / workflow 会持续分裂
- 高级功能会分散在不同表单里重复实现

推荐改成一个统一创建器，在内部根据任务类型决定显示哪些默认能力和高级能力。

## Suggested Data Contract Direction

为避免继续“补丁叠补丁”，建议后续的数据结构演进遵循两个原则：

### 原则 1：结构化优先

不要继续让前端只拼 `schedule_value` 字符串。应优先保留结构化语义，再由 builder 负责生成底层表达。

建议方向：

- `trigger_mode`
- `schedule_preset`
- `schedule_metadata`
- `action_kind`
- `action_spec`
- `delivery_mode`
- `delivery_targets`
- `approval_policy`
- `retry_policy`
- `guardrail_policy`

### 原则 2：override 与 definition 分离

像“跳过本次”“稍后提醒”这类操作不应直接改写原 job 定义，否则用户难以理解发生了什么。

建议方向：

- job 负责定义长期规则
- override 负责覆盖单次执行
- run 负责记录单次结果

## Rollout Priority

如果后续要实施，建议分三阶段推进：

### Phase 1

- 单次日期提醒
- 自定义调度编辑器
- 自然语言预览
- 列表中的“下次执行”强化展示

### Phase 2

- 动作类型选择器
- 技能选择器
- 多通道投递
- 测试一次

### Phase 3

- 审批策略
- 可见范围
- 连续失败保护
- 跳过本次 / 稍后提醒

## Non-Goals

本文档不包含以下内容：

- 工作流编排器细节
- 模板库设计
- 开放平台 / webhook 产品化细节
- 完整实现计划与任务拆解

## Decision Summary

自动化模块中的高级功能，应该从“零散附加字段”升级为“四组能力”：

- 调度高级功能：设准时间
- 执行高级功能：做对事情
- 投递高级功能：送到对的人和位置
- 治理高级功能：确保自动化可控

最优先的升级不是继续给现有高级区补字段，而是先把“调度编辑器”做成独立、一等的产品能力，再以统一创建器承接提醒、定时任务和事件任务的差异。
