# Chat History Tabbed Lists Design

## Context

当前工作区里的最近对话展示存在两个明显问题：

1. 侧边栏把普通对话、项目对话、桥接对话直接连续堆叠，信息层次弱，阅读路径混乱。
2. 项目对话相比普通对话携带更多附加信息，但当前仍沿用近似普通列表项的表现形式，导致标题、项目归属、状态标签和时间信息挤在一起，视觉上过密且不稳定。

用户希望把最近对话与对话模块历史列表统一改成按类型切换的结构，而不是“全部展开”；同时要求项目对话获得更适合承载附加信息的卡片样式。

## Goals

1. 将最近对话的三类内容改成通过顶部 Tab 切换，而不是同时展示。
2. 固定分类为 `普通对话`、`项目对话`、`桥接对话`，不提供 `全部` Tab。
3. 让侧边栏与对话列表页共享同一分类状态，并保持联动。
4. 为项目对话提供更宽松、信息分层更清晰的卡片样式。
5. 保持普通对话和桥接对话的列表密度较轻，避免无额外信息的条目被过度卡片化。

## Non-Goals

1. 不重新定义线程数据来源、后端筛选接口或线程归类规则。
2. 不在本次设计里引入新的对话类型。
3. 不把普通对话、项目对话、桥接对话统一做成同样重量级的卡片系统。
4. 不修改线程详情页、消息流或发送器区域。

## Product Decisions

### 1. Fixed Tab Taxonomy

工作区对话历史固定分为 3 类：

- `general` -> 普通对话
- `project` -> 项目对话
- `bridge` -> 桥接对话

不再提供 `全部` 聚合视图。用户必须先进入某个分类，再浏览、搜索和操作该分类中的线程。

### 2. One Shared Tab State Driven by URL

侧边栏最近对话与 `/workspace/chats` 列表页共享同一个分类状态，状态由 URL 查询参数驱动。

建议参数：

- `type=general`
- `type=project`
- `type=bridge`

选择 URL 驱动而不是本地 store 的原因：

1. 侧边栏和主列表页天然联动，不需要额外全局状态同步。
2. 刷新、前进后退、分享链接时都能保留当前分类。
3. 现有页面已经依赖查询参数表达线程上下文，延续同一模式更稳定。

默认值为 `general`。当 URL 缺省或值非法时，回退到 `general`。

### 3. Tabs Appear in Both Surfaces

Tab 需要同时出现在两个位置：

1. 侧边栏 `最近的对话` 标题下
2. 对话模块完整列表页的搜索区域上方

其中主列表页的 Tab 可视层级更高，作为该页面的主筛选控件；侧边栏版本保持紧凑，用于快速切换。

### 4. Search Works Within the Active Tab Only

搜索只过滤当前分类中的线程，而不是全局搜索所有线程。

行为上遵循：

1. 先按 `type` 选出当前分类的数据集
2. 再在该数据集上执行标题搜索
3. 搜索结果为空时，只展示当前分类的空结果状态

这样可以避免用户处于“项目对话”视角时，却被普通对话结果打断。

### 5. Project Threads Use an Information Card

项目对话采用“信息卡片”方案，而不是普通列表项加多个小 badge 的堆叠。

卡片信息层级如下：

1. 主标题：线程标题，只表达对话本身
2. 辅助信息区：项目归属、待回复等状态 badge
3. 时间信息：更新时间，退到视觉次级层

如果需要附加说明，也应以轻量辅助文本呈现，而不是把项目名和线程名压在一行主标题里。

### 6. General and Bridge Threads Stay Lightweight

普通对话和桥接对话保持较轻的列表项或轻卡片表现：

1. 标题为主
2. 时间为辅
3. 必要时显示一个附加 badge

这样可以保持扫描效率，并让项目对话在视觉上真正体现“信息更多，因此承载方式不同”。

### 7. Density Differs by Surface

相同的分类逻辑会同时服务侧边栏和主列表页，但两处视觉密度不同：

- 侧边栏：更紧凑，强调快速浏览与切换
- 主列表页：更宽松，强调阅读舒适度和信息分层

因此，本次设计不是追求两个页面完全同构，而是追求“结构一致、密度有别”。

## Interaction Rules

### 1. Selection Mode Is Scoped to the Active Tab

批量选择模式只作用于当前 Tab 当前可见的数据集：

1. `全选` 只选中当前分类且匹配当前搜索条件的线程
2. 切换 Tab 时清空当前选择
3. 不允许跨 Tab 保留批量选择结果

这样可以避免分类切换后，用户误删不可见数据。

### 2. Deletion Keeps the User in the Same Category

如果删除操作影响当前打开的线程：

1. 优先跳转到同一分类中的下一条剩余线程
2. 如果该分类已为空，则保留在当前列表页并展示该分类空状态
3. 不自动切到别的分类

这个规则同样适用于批量删除。原则是：用户既然在某个分类中操作，就不应该因为删除而被强制带离当前分类语境。

### 3. Pending Clarification Priority Stays Inside Each Tab

现有的 `待回复` 优先级保留，但仅在各自分类内部排序。

这意味着：

1. 项目对话内有待回复的线程，可以在项目对话 Tab 内优先
2. 不再通过跨分类混排把项目对话整体提前到普通对话之前

Tab 结构本身已经承担了一级分类职责，剩余排序应只在分类内部发生。

### 4. Empty States Are Category-Specific

每个 Tab 都应该有自己的空状态文案或空列表结果：

1. 当前分类本来就没有线程
2. 当前分类有线程，但被搜索过滤为空

不使用“自动跳转到有内容的别的分类”来掩盖空状态。

## UI Structure

### Sidebar Recent Chats

侧边栏最近对话区块结构：

1. 区块标题行：`最近的对话` + `选择`
2. 紧凑型 Tab 行：`普通对话` / `项目对话` / `桥接对话`
3. 当前分类列表
4. 选择模式工具条（仅在选择模式显示）

列表表现：

- 普通对话：轻量行式列表
- 桥接对话：轻量行式列表，保留桥接来源 badge
- 项目对话：紧凑信息卡片

项目对话卡片在侧边栏内应满足：

1. 有明显圆角和边界，但不能重到接近仪表盘组件
2. 标题独立一行
3. 项目 badge 与待回复 badge 位于一组辅助信息区
4. 更新时间单独退到次级文本层

### Chats List Page

完整列表页结构：

1. 顶部 Tab 行
2. 搜索框与 `选择` 控件
3. 选择模式工具条（条件显示）
4. 当前分类列表

列表表现：

- 普通对话：宽松列表项或轻卡片
- 桥接对话：宽松列表项或轻卡片
- 项目对话：完整信息卡片

主列表页中的项目卡片比侧边栏版本拥有更大的留白和更清晰的分区，但信息层级保持一致。

## Implementation Shape

### Frontend State and Utilities

需要引入一个共享的聊天类型枚举与解析函数，例如：

- `WorkspaceThreadType = "general" | "project" | "bridge"`
- 查询参数解析与默认值归一化函数
- 线程按类型分组或过滤的共享 helper

优先把“线程分类”和“当前类型过滤”抽成可复用逻辑，避免侧边栏和主列表页各自复制一份条件判断。

### Sidebar Component

`recent-chat-list.tsx` 需要重构为：

1. 先根据当前 URL 的 `type` 选出活跃分类
2. 渲染单个当前分类分组，而不是依次渲染所有分组
3. 在标题与列表之间插入 Tab 控件
4. 根据活跃分类切换不同列表项样式

### Chats Page Component

`src/app/workspace/chats/page.tsx` 需要：

1. 读取和维护相同的 `type` 查询参数
2. 在搜索框上方增加 Tab 控件
3. 按当前分类过滤列表与批量选择范围
4. 为项目对话渲染专用信息卡片，而不是沿用统一的平铺列表项

### Shared Presentation

建议抽出共享展示单元，例如：

1. 线程分类 Tab 组件
2. 项目对话卡片组件
3. 普通/桥接对话列表项组件

原因是本次设计引入了“同一结构，不同密度”的双场景复用。如果继续在两个页面里内联堆样式分支，很容易再次变成补丁叠补丁式修改。

## Testing

需要补的验证重点：

1. 合同测试锁定只有 3 个固定 Tab，且不存在 `全部`
2. 合同测试锁定侧边栏与主列表页都渲染 Tab
3. 合同测试锁定当前分类由查询参数驱动
4. 合同测试锁定搜索和批量选择只作用于当前分类
5. 合同测试锁定项目对话使用专门的信息卡片结构
6. 现有删除后跳转逻辑需要在按分类过滤后重新验证

## Refactor Note

这次改造不能只是在现有列表上继续叠条件渲染和额外样式类。

如果继续沿用“一个组件里同时渲染全部分组，再靠局部 patch 控制密度和状态”的方式，代码会很快回到当前的问题：结构耦合、视觉规则分散、删除/搜索/选择逻辑各写一套。

本次实现应优先做两层收敛：

1. 共享的 Tab 状态与线程类型过滤逻辑
2. 共享的列表展示单元与项目卡片展示单元

这样才能把这轮修改落成长期可维护的最优解，而不是补丁叠补丁。
