# 受控本机动作产品设计

日期：2026-04-15  
状态：Draft for review  
范围：`Desktop Local Actions / Goal-to-Action Planning / Permission Modes / Review Flow / Execution / Audit`

---

## 1. 设计结论

本设计的结论只有一句话：

> **Nion 不应该把本机能力做成任意控机代理，而应该把它做成“受控本机动作系统”。**

这里的关键词是：

- 受控
- 结构化
- 可审核
- 可自动执行
- 可追踪

它不是：

- 远程桌面
- SSH 替代品
- 任意鼠标/键盘模拟器
- 无边界系统代理

它是：

- 用户目标到结构化动作计划的编排系统
- 由 daemon 决策、由 desktop main 执行的本机动作控制平面
- 具有全局权限模式和完整审计能力的执行系统

---

## 2. 产品定义

`受控本机动作 = Nion 将用户目标翻译成一组结构化、可审计、可按权限执行的本机动作，用来代表用户操作自己的电脑。`

这个定义里最重要的不是“操作电脑”，而是：

- **先翻译成动作计划**
- **再按权限判断是否执行**
- **执行后一定回执和审计**

因此，产品主语应该始终是：

- 用户的目标
- Nion 生成的动作计划
- 系统根据权限模式决定执行方式

而不是：

- 某个工具调用
- 某个系统 API
- 某个隐藏的自动行为

---

## 3. 产品边界

### 3.1 目标场景

这条线主要服务于三类目标：

#### A. 看一眼

- 截图当前窗口
- 截图整个屏幕
- 浏览目录
- 搜索文件
- 查看文件基本信息

#### B. 整理一下

- 移动文件
- 批量移动文件
- 重命名文件
- 按规则整理下载目录
- 移到回收站
- 永久删除
- 清空目录
- 覆盖文件

#### C. 轻操作

- 打开应用
- 关闭应用
- 打开文件
- 打开目录
- 聚焦应用 / 窗口

### 3.2 明确排除

即使是完整版本，也明确不做：

- 任意鼠标坐标点击
- 任意键盘输入
- 持续屏幕监控
- 任意 shell 直通
- 不受目标边界约束的系统操作

原因不是做不到，而是：

> 一旦支持这些能力，产品会从“受控本机动作”退化成“通用控机代理”，权限、信任和审计边界都会显著恶化。

## 4. 方案比较与选择

### 4.1 方案 A：命令直通型

用户发指令，系统直接映射为本机操作。

优点：

- 实现快
- 行为直接

缺点：

- 对普通用户不友好
- 权限语义弱
- 审核体验碎片化

结论：

- 不采用

### 4.2 方案 B：目标驱动 + 动作编排型

用户给目标，系统先生成结构化动作计划，再根据权限模式决定：

- 拒绝
- 审核
- 直接执行

优点：

- 最符合普通用户心智
- 最适合三档权限模型
- 最容易和审计、回执、结果说明连接

缺点：

- 需要先定义动作模型和执行记录

结论：

- **采用**

### 4.3 方案 C：建议型助手

系统只分析和建议，不直接执行。

优点：

- 风险最低

缺点：

- 不满足 `全部允许` 模式下直接替用户完成目标的要求

结论：

- 不采用

## 5. 权限模型

本设计采用一个**全局三档权限模式**，不做分类权限。

权限入口位于：

- `Settings > Daemon`

三档权限定义如下。

### 5.1 完全禁止

行为：

- 不执行任何本机动作
- 可以分析目标
- 可以展示动作计划预览
- 明确告知用户当前权限禁止执行

适用：

- 用户暂时不信任本机动作系统
- 希望只看计划不执行

### 5.2 需要审核

行为：

- 先生成动作计划
- 显示风险摘要
- 用户审核后才执行

规则：

- 所有不可逆动作必须在审核面里显式列出
- 用户拒绝后绝不执行

适用：

- 默认模式
- 普通用户长期使用模式

### 5.3 全部允许

行为：

- 动作计划生成后直接执行
- 不等待确认
- 仍然回传结果并写审计日志

规则：

- 允许不可逆动作自动执行
- 但不可逆动作必须出现在执行回执和审计记录中

适用：

- 高信任模式
- 用户明确接受“系统可直接代表我完成本机目标”

### 5.4 默认策略

第一版默认权限模式必须是：

- **需要审核**

原因：

- `完全禁止` 太弱
- `全部允许` 风险太高
- `需要审核` 是能力和信任之间最稳的默认值

## 6. 动作模型

本系统的关键不是工具，而是动作计划。

### 6.1 核心对象

#### A. LocalActionGoal

表示用户目标。

建议字段：

- `goal_id`
- `source_surface`
- `source_channel`
- `user_input`
- `created_at`
- `status`

#### B. LocalActionPlan

表示动作计划。

建议字段：

- `plan_id`
- `goal_id`
- `summary`
- `risk_level`
- `requires_review`
- `actions[]`

#### C. LocalActionItem

表示单个动作。

建议字段：

- `action_id`
- `action_type`
- `target`
- `parameters`
- `reversible`
- `risk_level`
- `status`
- `result_summary`
- `error_reason`

#### D. LocalActionExecutionRecord

表示执行审计记录。

建议字段：

- `execution_id`
- `goal_id`
- `plan_id`
- `permission_mode`
- `approval_status`
- `executed_actions`
- `started_at`
- `finished_at`
- `has_irreversible_action`
- `audit_summary`

### 6.2 动作白名单

第一版只允许结构化白名单动作。

#### 截图类

- `capture_active_window`
- `capture_full_screen`
- `capture_app_window`

#### 文件浏览类

- `list_directory`
- `search_files`
- `inspect_file_metadata`

#### 文件整理类

- `move_file`
- `move_files_batch`
- `rename_file`
- `organize_downloads`
- `move_to_trash`
- `delete_permanently`
- `empty_directory`
- `overwrite_file`

#### 应用与窗口类

- `open_application`
- `close_application`
- `focus_application`
- `open_file`
- `open_directory`

### 6.3 目标边界原则

即使处于 `全部允许` 模式，系统也必须遵守：

> **只能执行完成当前目标所必需的动作计划，不能借机扩张动作范围。**

例如：

- 用户说“整理下载目录”
  - 可以搜索、分类、移动、删除下载目录中的文件
  - 不可以顺手清理桌面、关闭别的应用或改动无关目录

## 7. 审核流

在 `需要审核` 模式下，系统展示的是一个**动作计划审核卡片**，而不是模糊权限提示。

审核卡片至少包含：

- 本次目标
- 计划执行的动作数
- 不可逆动作数
- 风险等级摘要
- 影响范围
- 可选操作：
  - `批准执行`
  - `拒绝`
  - `查看详情`

### 7.1 审核粒度

推荐规则：

- 计划级审核为主
- 不可逆动作必须显式列出
- 极高风险批量操作可要求额外确认

### 7.2 三种模式下的交互

#### 完全禁止

用户看到：

- 当前本机动作权限为完全禁止
- 如果放开权限，将执行哪些动作

系统行为：

- 只生成计划
- 不执行

#### 需要审核

用户看到：

- 动作计划
- 风险摘要
- 不可逆动作清单

系统行为：

- 等待审核
- 审核通过后执行

#### 全部允许

用户看到：

- 无事前审核
- 只有执行结果回执

系统行为：

- 直接执行
- 回传结果
- 写审计日志

---

## 8. 执行回执与审计

### 8.1 执行回执

执行后，系统必须回传：

- 执行了哪些动作
- 成功多少
- 失败多少
- 是否包含不可逆动作
- 影响了哪些文件 / 窗口 / 应用
- 审计记录 ID

### 8.2 审计原则

既然支持不可逆动作，就必须默认留痕。

建议审计至少包含：

- 触发来源
- 时间
- 原始目标
- 动作计划摘要
- 权限模式
- 是否审核
- 不可逆动作清单
- 结果摘要
- 失败原因

### 8.3 日志保留建议

第一版可采用简单策略：

- 默认保留最近 90 天
- 可在桌面端查看
- 不要求复杂检索

## 9. 架构边界

### 9.1 daemon 负责

- 目标解析
- 动作计划生成
- 权限模式判断
- 审核状态机
- 审计记录
- 对外统一接口

### 9.2 desktop main 负责

- 真正执行本机动作
- 调用 OS / Electron / Finder / screenshot 等能力
- 返回执行结果

### 9.3 bridge / 远程入口负责

- 发起目标
- 展示审核卡片
- 展示执行回执

它们**不直接调用本机执行器**。

### 9.4 责任链

完整链路应是：

`用户目标 -> 动作计划 -> 权限判断 -> desktop main 执行 -> 回执 -> 审计`

---

## 10. 风控原则

### 10.1 默认模式

- 默认 `需要审核`

### 10.2 不可逆动作规则

- `需要审核` 下必须显式审核
- `全部允许` 下可直接执行
- 但必须进入回执和审计日志

### 10.3 风险透明

只要权限模式是 `全部允许`，产品必须在关键位置持续提示：

- 当前本机动作权限：全部允许

### 10.4 风险等级提高规则

建议至少按以下逻辑提升风险：

- 全屏截图 > 单窗口截图
- 批量移动 > 单文件移动
- 永久删除 > 移到回收站
- 清空目录 > 删除单个文件
- 覆盖文件 > 普通移动
- 关闭应用 > 打开应用

## 12. 完整版本范围

这一条线不拆版本，直接按完整版本定义。

完整版本必须同时具备：

1. 统一权限中心
2. 完整动作编排链
3. 三类动作全部成立
4. 所有入口行为一致
5. 审核与回执完整
6. 审计与追溯完整

如果这六项中任何一项不成立，就不算完整版本。

---

## 13. 验收标准

### 13.1 权限验收

三档模式行为必须稳定：

- 完全禁止
- 需要审核
- 全部允许

### 13.2 动作验收

看一眼、整理一下、轻操作三类动作都必须真实可用。

### 13.3 审核验收

在 `需要审核` 模式下：

- 用户能看懂动作计划
- 用户能看见不可逆动作
- 用户能批准 / 拒绝
- 系统按审核结果执行或拒绝

### 13.4 回执与审计验收

执行后必须：

- 返回可理解的回执
- 留下审计记录
- 明确标注不可逆动作

### 13.5 一致性验收

无论从：

- 远程入口
- 桌面端
- 自动化任务

触发，都必须服从同一套权限模式、动作计划和审计逻辑。

---

## 14. 最终判断

这条线真正要交付的不是：

- 一个更强的系统工具
- 一个任意控机代理

而是：

> **一个能把用户目标翻译成结构化本机动作计划，并按全局权限模式执行、审核、回执和审计的完整动作系统。**

如果后续实现偏离这个判断，就会重新滑向：

- 动作很多
- 但边界很差
- 用户不敢开权限
- 一旦出问题无法回溯

这会直接破坏它作为值守模式能力延展线的长期价值。
