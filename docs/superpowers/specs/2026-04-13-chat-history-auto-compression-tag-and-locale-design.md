# 聊天历史自动压缩 Tag 与语言合同设计

日期：2026-04-13  
状态：Draft for review  
范围：`Chat timeline / thread stream context / summarization contract`

---

## 1. 背景

当前自动压缩历史对话的体验有两个直接问题：

1. 自动压缩摘要有时会在时间线里以一整段正文直接露出，而不是退化成低干扰的系统标记。
2. 中文界面下生成的自动压缩摘要仍可能是英文，说明摘要语言没有服从明确的产品语言合同。

这两个问题叠加后，用户会感知到明显的“系统内部机制漏出来了”：

- 时间线被大段内部摘要打断
- 摘要语种与界面不一致
- 自动压缩不再是无感背景能力，而变成了前台噪音

本设计的目标不是只修一个显示 bug，而是把“自动压缩摘要”收口为一条正式的内部消息合同。

---

## 2. 已确认决策

本轮设计基于以下用户已确认决策：

1. 自动压缩摘要在时间线默认只显示为一个小 tag，而不是完整正文。
2. 该 tag 可以点击展开，再次点击可以收起。
3. 展开后显示摘要正文，但仍然保持“系统内部信息”观感，不能伪装成普通 assistant 回复。
4. 摘要语言跟随界面/用户设置语言，而不是跟随该段对话的主要语言。
5. 摘要一旦生成，正文语言固定；之后切换界面语言时，历史摘要正文不做动态翻译。
6. 历史旧 thread 不做批量迁移，采用“读旧写新”策略。

---

## 3. 目标与非目标

### 3.1 目标

本轮要同时达成四件事：

1. 自动压缩摘要在时间线默认退化为低干扰 tag。
2. 用户可以在原地展开/收起单条摘要。
3. 新生成摘要的语言严格服从当前界面语言。
4. 历史旧格式摘要不会因为新 UI 切换而重新露出大段正文。

### 3.2 非目标

本轮不做以下事情：

1. 不为历史摘要做批量重写或离线迁移。
2. 不在前端增加“运行时翻译历史摘要”的额外层。
3. 不把自动压缩摘要升级成新的对话卡片类型或独立页面。
4. 不修改 summarization 的触发策略、保留窗口或模型选择策略。

---

## 4. 设计总览

推荐方案是把自动压缩摘要收口成**正式内部摘要合同**：

1. 前端在消息分组层把该消息识别为 `system:internal-summary`。
2. 时间线默认只渲染一个居中的紧凑 tag。
3. tag 被点击时，在原位置展开同一条摘要消息的正文。
4. 后端在生成摘要时显式接收 `locale`，并把摘要正文与 `summary_locale` 一起写入消息元数据。

这条路径比“只修前端识别”更完整，也比“前端运行时翻译历史摘要”更干净，因为它把语言来源和展示边界都收敛成正式合同，而不是继续让前端猜。

---

## 5. 交互设计

### 5.1 默认态

自动压缩摘要在时间线里默认显示为一个低干扰、居中的小 tag：

- 中文界面：`已自动压缩`
- 英文界面：`Auto-compressed`

这个 tag 不是聊天气泡，不占用 assistant / user 的说话位。它应被理解为“系统在后台做过一次上下文压缩”的提示，而不是“系统正在对你说一句话”。

### 5.2 展开态

点击 tag 后，在原位置展开摘要正文：

- 展开内容属于同一条时间线项，不创建新的 message bubble
- 再次点击 tag 可收起
- 一条 thread 中出现多次自动压缩时，每条摘要各自独立控制展开态

### 5.3 视觉语义

展开后的摘要正文仍应维持内部信息语义：

- 使用弱对比度容器
- 视觉权重低于普通 assistant 回复
- 不出现“复制这条 assistant 回答”之类的普通回复 affordance
- 不混入 human / assistant 的头像、对齐方式或气泡语言

目标是“可查，但不抢戏”。

---

## 6. 数据合同

### 6.1 消息分类

自动压缩摘要在前端继续归入 `system:internal-summary`，但识别规则升级为：

1. **优先读取结构化元数据**  
   新合同下，只要消息元数据明确声明该消息是内部压缩摘要，前端必须直接按内部摘要处理。

2. **兼容旧文本格式**  
   如果没有新元数据，则继续兼容旧格式识别，包括：
   - `Here is a summary of the conversation to date:`
   - `Conversation Summary` 及其已知英文 section headings

这样可以保证旧 thread 不回归成大段正文。

### 6.2 新摘要消息元数据

新生成的摘要消息应把与展示直接相关的数据放在**该消息自身**的 `additional_kwargs` 中，而不是写到 thread 级旁路状态。建议至少包含：

- `internal_summary: true`
- `summary_locale: "zh-CN" | "en-US"`
- `summary_format_version: 1`

如果后续需要，还可以在同一处扩展其他内部摘要元数据，而不影响 thread 顶层模型。

### 6.3 展示原则

前端展开逻辑只消费当前摘要消息自身的数据：

- tag 文案跟随当前 UI locale
- 摘要正文跟随该消息自身的正文内容
- 摘要语言以该消息的 `summary_locale` 为准

前端不额外发请求，不做二次翻译，不依赖 thread 级全局字段补全。

---

## 7. 摘要语言合同

### 7.1 语言来源

摘要生成语言以**界面/用户设置语言**为权威来源，而不是该段对话的主语言。

因此，thread submit 时必须把当前 `locale` 放入请求 `context`，使 summarization 成为显式消费该字段的运行时能力，而不是依赖模型从上下文猜测。

### 7.2 生成行为

当 `locale=zh-CN` 时，自动压缩摘要应输出中文结构与中文正文。  
当 `locale=en-US` 时，自动压缩摘要应输出英文结构与英文正文。

这一点应体现在 summarization prompt 或其上层包装逻辑中，而不是仅依赖 prompt 默认英文模板。

### 7.3 历史稳定性

摘要一旦生成，其正文语言保持不变：

- 用户之后切换 UI 语言
- tag 文案跟随 UI 语言变化
- 已生成摘要正文仍按原始语言展示

这保证历史 thread 的内容稳定，不会因为 UI 切换而发生语义漂移。

---

## 8. 异常与回退策略

### 8.1 缺少 `summary_locale`

如果某条新摘要消息被识别为内部摘要，但缺少 `summary_locale`：

- tag 仍照常显示
- 展开时直接显示原始正文
- 不做前端翻译猜测

### 8.2 旧格式摘要

如果消息没有结构化元数据，但正文命中旧摘要格式：

- 仍归类为 `system:internal-summary`
- 默认显示 tag
- 展开时显示旧正文

### 8.3 空摘要或解析失败

如果正文为空，或结构无法稳定提取：

- 只显示 tag
- 不展示空白展开面板

这比把一块空容器塞进时间线更稳妥。

---

## 9. 迁移策略

采用“读旧写新”，不做一次性迁移：

1. **新写入**  
   后端从切换点开始只生成新内部摘要合同，并写入 `summary_locale` 等元数据。

2. **旧读取**  
   前端保留旧格式兼容识别逻辑。

3. **不回填历史**  
   不批量扫描已有 threads 重写消息内容，不引入迁移脚本。

这样可以避免高风险历史数据修改，同时让未来行为从合同层面统一。

---

## 10. 测试与验收

### 10.1 前端测试

需要补齐至少三类测试：

1. 新内部摘要合同会被归类为 `system:internal-summary`
2. tag 支持展开/收起，且不会渲染成普通 human / assistant message
3. 旧英文摘要格式仍被兼容识别

### 10.2 后端测试

需要补齐至少两类测试：

1. summarization 在收到 `locale=zh-CN` 时生成中文结构
2. 摘要消息会携带 `summary_locale` 元数据

### 10.3 验收标准

上线后满足以下标准才算完成：

1. 默认时间线只显示小 tag，不出现大段压缩摘要正文
2. 点击 tag 可以原地展开/收起摘要
3. 中文界面下新生成摘要为中文
4. 已生成的中文摘要在之后切到英文界面时仍显示中文正文
5. 历史旧 thread 不因新 UI 切换而退化成大段正文

---

## 11. 风险与约束

### 11.1 最大风险

当前最大风险不是交互，而是**合同分裂**：

- 前端用一套文本启发式识别摘要
- 后端又生成另一套格式
- 语言来源没有正式进入请求上下文

如果只做局部补丁，后面还会继续出现“又有一种摘要格式没被识别”的回归。

### 11.2 本设计的约束

本设计要求：

1. `locale` 进入 thread submit `context`
2. 新摘要消息写入结构化元数据
3. 前端从“纯文本猜测识别”升级到“优先结构化识别，兼容旧文本”

这三条缺一不可。少做任何一条，都会把问题重新推回补丁层。

---

## 12. 实施建议

实现顺序建议如下：

1. 先定义并测试新内部摘要消息合同
2. 再把前端渲染从静态 tag 扩展为可展开 tag
3. 再把 `locale` 接入 thread submit `context`
4. 最后调整 summarization 生成逻辑与后端测试

原因是：必须先锁住合同，再做交互和语言生成，否则又会落回“前后端各补一点”的失控状态。
