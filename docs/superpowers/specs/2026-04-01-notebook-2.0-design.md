# Notebook 2.0 Design

## 背景

Notebook 当前已经是 Nion 里完成度较高的一条产品线：

- 本地优先
- Markdown 知识库
- 目录树
- 编辑器
- 历史版本
- 回收站
- quick capture
- assist preview / apply
- chat import
- note-scoped notebook assistant

但它仍然主要是“一个功能完整的笔记模块”，还不是“agent-native knowledge workspace”。

结合前面的两份设计：

- [knowledge-work-object-model-design.md](/Users/zhangtiancheng/Documents/项目/agent/nion/docs/superpowers/specs/2026-04-01-knowledge-work-object-model-design.md)
- [notebook-project-bridge-actions-design.md](/Users/zhangtiancheng/Documents/项目/agent/nion/docs/superpowers/specs/2026-04-01-notebook-project-bridge-actions-design.md)

Notebook 2.0 的目标不应该是“再多几个按钮”，而应该是把 Notebook 升级成：

- agent 可理解的知识对象域
- 可被引用、提炼、桥接、导出的知识工作台
- 通用办公 agent 的主要知识底座之一

## 目标

把 Notebook 从“本地 Markdown 笔记模块”升级成“Nion 的 agent-native knowledge workspace”。

Notebook 2.0 要做到：

- 用户仍然拥有 Notebook
- agent 能更强地使用 Notebook
- Notebook 能被 Project / Memory / runtime 正式引用
- 知识不再只是文件，而是可检索、可引用、可提炼、可导出的一级对象

## 非目标

这份设计不处理：

- global Memory provider 演进
- Project 2.0 dashboard 重构
- SkillTool 实现
- Prompt Runtime / Tool Runtime / Hook Event Plane 的内部技术细节

这份设计只处理 Notebook 作为产品对象层的升级方向。

## 设计原则

### 1. Notebook 仍然是用户资产

Notebook 2.0 必须保留这个核心边界：

- Notebook 不是 agent memory
- Notebook 不默认被 agent 自动写入
- agent 是 assistant，不是 owner

### 2. Notebook 不是静态仓库，而是知识工作台

Notebook 不应只承担：

- 存储
- 编辑
- 回收站

它还应承担：

- 检索
- 引用
- 聚合
- 提炼
- 导出
- 跨对象桥接

### 3. 先对象化，再 UI 化

Notebook 2.0 的本质升级应该先体现在：

- note
- fragment
- reference
- candidate
- bridge action

而不是先体现在视觉重做。

### 4. 先服务通用办公场景

Notebook 2.0 优先服务：

- 资料整理
- 会议记录
- 研究摘要
- 行动项沉淀
- 方案对比
- 项目证据管理

而不是先服务 code-only 工作流。

## Notebook 2.0 的定义

Notebook 2.0 是一个本地优先、用户拥有、agent 可操作的知识工作台。

它的最小对象层应包括：

- `Note`
- `NoteFragment`
- `ReferenceLink`
- `DraftCandidate`
- `ExtractionCandidate`

其中：

- `Note` 仍然是 Notebook 的主对象
- `NoteFragment` 是 future 检索、引用、提炼的基础粒度
- `ReferenceLink` 是跨对象关系
- `DraftCandidate` 是 bridge/export 的安全落点
- `ExtractionCandidate` 是知识提炼的中间态

## 现状问题清单

### 问题 1：检索仍偏目录/文件思维

当前 sidebar 搜索主要还是基于：

- path
- name

这说明 Notebook 还停留在文件树思维，而不是知识检索思维。

### 问题 2：引用与来源链不完整

当前 Notebook 可以：

- 导入 chat
- assist apply

但“这段内容来自哪里、后来流向哪里”还没有被正式建模。

### 问题 3：assist 仍偏 note-local

Notebook assistant 当前更像：

- note-scoped rewrite / QA shell

而不是：

- 可围绕 note collection、fragments、references、projects 做更高阶知识工作

### 问题 4：和 Project / Memory 的桥接尚未产品化

对象模型和 bridge action 已经设计出来，但 Notebook 产品层还没有消费这些动作。

### 问题 5：视图仍偏“笔记列表页”

Notebook 当前仍偏：

- tree
- recent
- note detail

还缺更强的知识工作视角。

## Notebook 2.0 的核心能力层

建议分成 5 层能力。

### A. Retrieval Layer

解决“找得到”。

### B. Reference Layer

解决“知道它从哪里来、和哪里有关”。

### C. Assistant Layer

解决“agent 如何围绕 note 工作，而不只是改写正文”。

### D. Bridge Layer

解决“Notebook 如何和 Project / Memory / future SkillTool 正式互转”。

### E. Review / Export Layer

解决“提炼、确认、导出、沉淀”的产品化链路。

## 1. Retrieval Layer

Notebook 2.0 的第一大升级，不是 UI，而是 retrieval。

### 目标

从“树 + 文件名搜索”升级成“知识检索”。

### 能力

1. 全文检索
2. note fragment 检索
3. 语义检索
4. 混合检索排序
5. 过滤维度：
   - directory
   - tags
   - time
   - project linkage
   - recently referenced

### 返回结果

搜索结果不应只返回 note 标题，而应返回：

- note title
- matched fragment snippet
- fragment location
- why matched
- linked references

### 非目标

第一版不要求引入复杂向量数据库产品壳，但要先定义 retrieval contract。

## 2. Reference Layer

Notebook 2.0 需要正式支持 reference，而不是只靠用户手工复制路径。

### 能力

1. note -> project reference
2. note -> thread reference
3. note -> artifact reference
4. note -> memory extraction provenance
5. fragment-level citation

### 最小模型

```python
@dataclass(slots=True)
class NotebookReferenceLink:
    id: str
    note_id: str
    fragment_id: str | None
    target_object_type: Literal["project", "thread", "artifact", "memory_candidate"]
    target_object_id: str
    relation: str
    created_at: str
```

### 结果

Notebook 不只是“写了什么”，还要能回答：

- 被哪个项目引用
- 从哪个线程导入
- 生成过哪些 candidate

## 3. Assistant Layer

Notebook assistant 当前重点是 note-local rewrite flow，这个方向是对的，但 2.0 需要把能力往知识工作台拉高一层。

### 保留的能力

- note-scoped QA
- rewrite apply / confirm / cancel
- selection-based rewrite

### 升级的能力

1. multi-note summarize
2. compare notes
3. extract action items
4. extract constraints / risks / decisions
5. generate bridge candidates

### 关键原则

Notebook assistant 不能一开始就变成 full chat clone。

它仍然要保持：

- lightweight
- note-centric
- low surface area

但输出类型应该丰富：

- answer
- rewrite
- extraction candidate
- bridge candidate

## 4. Bridge Layer

这层直接消费：

- [notebook-project-bridge-actions-design.md](/Users/zhangtiancheng/Documents/项目/agent/nion/docs/superpowers/specs/2026-04-01-notebook-project-bridge-actions-design.md)

Notebook 2.0 至少应在产品层显式支持：

### Notebook -> Project

- 从当前 note 创建 Project draft
- 从当前 note 创建 Plan draft
- 从当前 note 提炼 project constraints

### Notebook -> Memory

- 从当前 note 提炼 long-term memory candidate

### Project -> Notebook

- 把项目总结导出为 Notebook draft
- 把项目复盘导出为 Notebook draft

### 关键要求

所有这类动作都应走：

- candidate
- review
- confirm

而不是直接落库。

## 5. Review / Export Layer

Notebook 2.0 需要一条完整的 review / export lane。

### 典型动作

- 导出草稿到 note
- 接受/拒绝 extraction candidate
- 把 note 绑定到 project
- 把 note 标记为高价值 reference

### 产物类型

- NotebookDraftCandidate
- MemoryEntryCandidate
- ProjectDraftCandidate
- ProjectConstraintCandidate

### 结果

Notebook 从“终点”变成“知识加工站”。

## 视图体系

Notebook 2.0 不应只有 sidebar/tree/editor 这一套视图。

建议逐步引入这些视图：

### 1. Inbox

- 快速记录
- 待整理
- 待分类

### 2. Recent

- 最近编辑
- 最近引用
- 最近导入

### 3. References

- 被项目引用的 notes
- 被 thread 导入的 notes

### 4. By Project

- 每个 project 关联的 notes / drafts / references

### 5. Extraction Queue

- 待确认的 memory / project / skill candidates

## Notebook 与 Project / Memory 的边界再确认

### Notebook 不做什么

- 不直接承担长期记忆
- 不承担项目状态推进
- 不替代 Project

### Notebook 负责什么

- 证据
- 草稿
- 资料
- 引用
- 提炼源

### Notebook 和 Memory 的关系

- Notebook 是 memory 的候选来源之一
- 但不是 memory 本身

### Notebook 和 Project 的关系

- Notebook 为 Project 提供资料、证据、草稿、提炼来源
- Project 为 Notebook 提供导出目标和引用目标

## 与现有模块的映射

### `NotebookService`

保留角色：

- note / directory / trash / metadata / move / restore

未来要扩的不是它直接去做一切，而是围绕它增加：

- fragment indexing
- reference linking
- bridge candidate persistence

### `NotebookAssistantService`

保留角色：

- rewrite pending flow
- apply / cancel / confirm

未来扩展方向：

- candidate generation
- extraction flow

### `/api/notebook/*`

未来 API 不应只停留在 CRUD。

需要逐步补：

- retrieval
- references
- extraction candidates
- bridge actions

## 验收标准

### A. 检索验收

1. Notebook 不再只有 path/name 搜索
2. 搜索结果能返回 fragment 和引用上下文

### B. 引用验收

3. note 与 project/thread/artifact 之间存在正式 reference link
4. 用户能看见某篇 note 的来源与去向

### C. Assistant 验收

5. notebook assistant 不再只会 note-local QA / rewrite
6. 能输出 extraction candidate / bridge candidate

### D. Bridge 验收

7. Notebook 2.0 可直接消费 bridge actions contract
8. 高风险跨对象动作仍是 draft-first / candidate-first

### E. 边界验收

9. Notebook 仍然是用户资产
10. Notebook 不默认写入 Memory 或 Project

## 风险与取舍

### 风险 1：一下子把 Notebook 做成“全能工作台”

处理方式：

- 先把 retrieval / references / bridge candidate 三件事做出来
- 不一开始把所有对象层 UI 都塞进 Notebook

### 风险 2：让 Notebook assistant 变成 full chat clone

处理方式：

- 保持 lightweight note-centric shell
- 扩能力，不扩产品壳

### 风险 3：先做 UI 再补对象能力

处理方式：

- 先定义 contract 和 candidate
- 再做视图
