# Projects 2.0 Design

## 背景

Projects 当前已经不是一个空壳模块，它已经具备相当多的基础能力：

- 项目列表
- 项目驾驶舱
- execution plans
- project threads
- timeline
- decision / confirmation flow
- managed artifacts
- project memory summary
- completion extraction suggestions

但它现在仍更像“长期工作容器页面”，而不是“agent execution workspace”。

结合下面这些已有结论：

- [knowledge-work-object-model-design.md](/Users/zhangtiancheng/Documents/项目/agent/nion/docs/superpowers/specs/2026-04-01-knowledge-work-object-model-design.md)
- [notebook-project-bridge-actions-design.md](/Users/zhangtiancheng/Documents/项目/agent/nion/docs/superpowers/specs/2026-04-01-notebook-project-bridge-actions-design.md)
- [claude-code-replication-roadmap-v2.md](/Users/zhangtiancheng/Documents/项目/agent/nion/docs/superpowers/plans/2026-04-01-claude-code-replication-roadmap-v2.md)

Projects 2.0 的任务不是“把 dashboard 做得更复杂”，而是把 Project 真正提升成：

- 可恢复
- 可治理
- 可分工
- 可提炼
- 可证明状态来源

的 agent execution workspace。

## 目标

把 Projects 从“长期工作模块”升级成“Nion 的 agent execution workspace”。

这意味着 Projects 2.0 必须能承载：

- 长期目标
- 多计划执行
- 多线程协作
- 决策与审批
- 项目内记忆
- 受管产物
- 完成与提炼
- 与 Notebook / Memory / SkillCandidate 的桥接

## 非目标

这份设计不处理：

- Prompt Runtime / Tool Runtime / Hook Event Plane 的底层实现
- Notebook 2.0 细节
- SkillTool 执行协议
- plugin / MCP 扩展面
- 纯 code-agent 专属 specialist lane

它只处理 Project 作为对象层与产品面的升级。

## 设计原则

### 1. Project 是 execution workspace，不是 dashboard 页面

项目页不是信息看板，而是长期工作执行空间。

### 2. 项目状态必须来自 runtime-derived state，而不是启发式拼装

如果用户问“项目为什么是这个状态”，系统必须能回答：

- 来自哪个 plan
- 来自哪个 thread
- 来自哪个 decision
- 来自哪个 artifact
- 来自哪个 memory / blocker

### 3. Project 不替代 Notebook，也不替代 Memory

Project 是执行容器。

- Notebook 是知识资产
- Memory 是 durable facts

Project 负责桥接，不负责吞并。

### 4. completion lane 必须是一等能力

完成一个项目，不应该只是改个字段，而应该触发：

- verify
- unresolved check
- extraction
- archive or keep warm

### 5. 先 execution semantics，后页面美化

Projects 2.0 的真正升级不在配色和布局，而在：

- plan semantics
- decision semantics
- thread semantics
- artifact semantics
- runtime-derived state

## 现状问题清单

### 问题 1：progress 仍偏启发式

当前 `ProjectDashboard.progress` 更像阶段百分比，而不是真实 execution state。

这会导致：

- 好看但不可靠
- 用户无法判断项目到底有没有推进

### 问题 2：`next_action` 不是 runtime-derived

当前 `next_action` 仍主要依赖 repository/service 启发式生成，而不是来自真实执行图。

### 问题 3：thread 还没有成为真正的执行 lane

Project thread 现在已经存在，但更多还是：

- primary
- exploration
- implementation
- review
- temporary

的标签化区分，还没有成为真正的 execution lanes。

### 问题 4：project memory 仍偏摘要投影

`project_memory_summary` 已存在，但它更像 dashboard projection，不是完整 project memory domain 的主对象面。

### 问题 5：completion 提炼还不是正式 completion lane

当前完成后会给出：

- `extract_long_term_memory`
- `extract_skill`

这说明方向对，但还没形成完整 completion lane contract。

## Projects 2.0 的核心能力层

建议分成 6 层。

### A. State Layer

回答“项目现在处于什么状态，为什么是这样”。

### B. Plan Layer

回答“接下来有哪些执行路线，谁是主线，什么被阻塞了”。

### C. Thread / Lane Layer

回答“哪些执行 lane 在推进项目”。

### D. Decision Layer

回答“当前有哪些需要人确认的关键决策”。

### E. Artifact / Memory Layer

回答“项目产出了什么，记住了什么，这些东西和执行如何关联”。

### F. Completion / Extraction Layer

回答“项目怎么完成，完成后如何提炼和归档”。

## 1. State Layer

Projects 2.0 需要放弃单纯的 phase 百分比心智，升级成 runtime-derived state。

### 最小状态维度

建议至少有：

- `lifecycle_status`
- `current_phase`
- `execution_health`
- `blocker_state`
- `decision_debt`
- `artifact_freshness`
- `memory_freshness`

### `execution_health`

建议不是百分比，而是：

- `healthy`
- `watch`
- `degraded`
- `blocked`

来源：

- primary plan 状态
- active thread 状态
- pending decisions
- unresolved blockers

### `decision_debt`

表示当前有多少关键决策没有处理，影响项目继续推进。

### `artifact_freshness`

表示主 artifact 是否已经落后于当前 project state。

## 2. Plan Layer

Project 2.0 里的 plan 不应只是列表，而应是执行路线系统。

### 能力

1. primary plan
2. gate plan
3. rework plan
4. dependency graph
5. branch route

### 要求

每个 plan 至少回答：

- 这条 plan 属于哪个 phase
- 是主线还是支线
- 当前状态是什么
- 被什么阻塞
- 下一步是什么
- 关联哪些 thread / artifact / decisions

### 目标

用户看到 plan 时，能理解：

- 项目现在走哪条主线
- 其他 plan 为什么存在
- 为什么当前卡在这里

## 3. Thread / Lane Layer

Project thread 需要从“有 role 的聊天线程”升级成“执行 lane”。

### 建议 lane

- `primary`
- `exploration`
- `implementation`
- `review`
- `handoff`
- `temporary`

### lane 必须具备的字段

- title
- role
- scope
- linked_plan_ids
- summary
- last_outcome
- latest_activity
- health

### 关键原则

thread 不应只展示 `thread_id` 或简单 role，而应回答：

- 这个 lane 负责什么
- 最近推进到了哪里
- 是否还活着
- 是否还值得继续

## 4. Decision Layer

Projects 2.0 里，decision 不能只是确认弹窗，它必须是一级对象。

### decision 至少应包括

- `type`
- `title`
- `summary`
- `related_plan_id`
- `payload`
- `actions`
- `status`
- `resolved_at`
- `resolution`
- `why_now`
- `impact`

### 关键动作类型

- `confirm_plan_outcome`
- `create_rework_plan`
- `extract_long_term_memory`
- `extract_skill`
- `complete_project`
- future:
  - `archive_project`
  - `confirm_route_change`

### 目标

用户能看懂：

- 为什么现在要做这个决定
- 不做会怎样
- 这个决定会改哪些对象状态

## 5. Artifact / Memory Layer

Projects 2.0 必须把 artifact 和 project memory 都正式纳入主链路。

### Artifact

当前已具备：

- managed artifact
- versions
- restore

2.0 要求补强：

- artifact lineage
- linked plan
- linked thread
- restore impact preview
- freshness state

### Project Memory

当前 `project_memory_summary` 不够。

Projects 2.0 需要：

- `ProjectMemoryEntry`
- category
- provenance
- relation to plan / phase / thread / artifact
- summary projection

### 关键目标

用户看到项目内记忆时，不应只看到一段 summary，而应知道：

- 是谁提炼的
- 来自哪个执行对象
- 是否已升级到 global Memory

## 6. Completion / Extraction Layer

Projects 2.0 必须把 completion 变成一条 gated lane。

### completion lane 的典型步骤

1. verify outputs
2. unresolved items check
3. project memory extraction
4. long-term memory extraction candidate
5. skill candidate extraction
6. archive / keep warm 决策

### 关键要求

- `complete_project` 不应只是把 lifecycle_status 改成 completed
- 所有后续提炼动作都应有 provenance
- completion 之后，项目要么进入 `completed`
- 要么进入 `completed_with_followups` 的类似心智

## 和 Notebook / Memory 的关系

### Project -> Notebook

Projects 2.0 应正式支持：

- summary export
- retro export
- decision log export

但都应通过 draft candidate，而不是直接写 note。

### Project -> Memory

Projects 2.0 应正式支持：

- `extract_long_term_memory_from_project`

且默认是 candidate-first。

### Project -> SkillCandidate

Projects 2.0 应把：

- `extract_skill_candidate_from_project`

纳入 completion lane，而不是继续作为孤立决策。

## 与现有模块的映射

### `ProjectRepository`

保留角色：

- persistence
- CRUD

未来扩展方向：

- 不再只生成启发式 dashboard projection
- 更多承载结构化 state / links / lineage

### `/api/projects/*`

当前已经很好，但 2.0 要求逐步增加：

- richer state
- richer lane/thread metadata
- bridge candidate APIs
- project memory detail APIs

### `frontend/src/core/projects/api.ts`

未来要能消费的不只是当前 dashboard payload，还包括：

- lane summaries
- artifact freshness
- decision why_now / impact
- bridge/export candidates

## 验收标准

### A. 状态验收

1. 项目状态不再只依赖启发式 phase 百分比
2. 用户能理解项目当前状态来自哪些 runtime 事实

### B. Plan / Lane 验收

3. plan 不再只是列表，而是执行路线系统
4. thread 不再只是聊天线程，而是 execution lane

### C. Decision 验收

5. decision 成为一级对象，而不是临时确认框
6. 用户能看懂 `why_now` / `impact`

### D. Artifact / Memory 验收

7. artifact / project memory 进入主链路
8. `project_memory_summary` 不再只是黑箱投影

### E. Completion 验收

9. completion lane 是正式流程，不是单个按钮
10. long-term memory / skill candidate 提炼有显式来源链

## 风险与取舍

### 风险 1：试图一次性把 Projects 做成“项目操作系统”

处理方式：

- 先补 execution semantics
- 再补 richer UI

### 风险 2：继续让 dashboard projection 掩盖真实状态

处理方式：

- 优先设计 runtime-derived state 字段

### 风险 3：让 Projects 吞并 Notebook / Memory

处理方式：

- 明确 Project 负责 bridge，不负责吞并
