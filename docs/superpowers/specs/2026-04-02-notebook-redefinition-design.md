# Notebook Redefinition Design

## 背景

在前面的探索中，Notebook 一度被拉向过多方向：

- 纯 Markdown 笔记编辑器
- 项目执行与收口的前置输入层
- 长期记忆提炼入口
- agent 工作流中的对象桥接层

这些方向叠加在一起，会直接带来两个问题：

1. 产品定位漂移
2. 普通用户心智过重

对当前阶段的 Nion 来说，继续沿着 `Notebook 2.0 / Projects 2.0 / object bridge / completion lane` 这条线堆功能，会让 Notebook 偏离最核心、最自然、也最可被普通用户理解的价值。

当前已经确认的真实判断是：

- Notebook 和 Memory 不是一回事
- Notebook 属于用户拥有的个人知识库
- Notebook 也承担个人工作材料库的职责
- 用户应能显式把聊天内容沉淀为笔记
- 用户也应能显式把工作空间中的产物保存到 Notebook
- 但这些动作都必须由用户明确发起，而不是系统自动执行

因此需要一份全新的 Notebook 定义设计，把 Notebook 从偏复杂的对象层桥接心智，重新拉回用户价值本身。

## 目标

重新定义 Notebook 模块，使它成为：

- 用户拥有的个人知识库
- 用户拥有的工作材料库
- AI 协助整理与加工的内容工作台

并明确：

- Notebook 的正式定位
- Notebook 和 Memory / Chat / Workspace 的边界
- Notebook 的核心对象模型
- Notebook 的核心用户流程
- Notebook assistant 的角色
- Notebook 首页与产品心智

## 非目标

这份设计不处理：

- 项目管理模块
- 项目状态机
- completion lane
- Candidate Center
- 长期记忆自动提炼
- object bridge / 跨对象治理
- plugin / MCP 扩展面

这份设计只负责：

- 重新定义 Notebook 自己

## 核心判断

Notebook 不应该被定义成：

- 项目模块的前置输入框
- 长期记忆数据库
- 工作空间文件系统镜像
- agent 工作流控制台

Notebook 最适合的定义是：

**用户拥有的个人知识与工作材料库。**

更完整地说：

**Notebook 是 Nion 中用户拥有的个人知识与工作材料空间，用于显式保存、整理、加工、检索和复用值得长期保留的内容。**

## 产品定位

### 1. Notebook 是用户资产库

Notebook 的本质是用户资产，而不是系统状态。

它承载：

- 用户写下来的内容
- 用户想长期保留的聊天沉淀
- 用户主动归档的工作材料
- 这些内容在后续加工后的版本

### 2. Notebook 是内容工作台

Notebook 不是被动存储柜，它也是内容加工台。

用户可以在里面：

- 写
- 改
- 总结
- 整理
- 搜索
- 归档
- 再利用

### 3. Notebook 是面向普通人的产品域

Notebook 的使用不应依赖：

- 项目状态机理解
- agent 运行时心智
- memory provider 理解
- 复杂治理流程

它应该是普通用户一看就能理解的：

**“这是我自己的知识与材料库。”**

## 它不是哪些东西

为了避免将来继续跑偏，这些边界需要明确写死。

### 1. 不是 Memory

Memory：

- 面向 agent runtime
- 偏短、偏结构化、偏事实
- 偏用户偏好、稳定规则、长期上下文

Notebook：

- 面向用户
- 偏完整、偏文档化、偏材料
- 偏用户主动保留的内容资产

一句话：

**Memory 是给 agent 用的，Notebook 是给用户用的。**

### 2. 不是项目管理器

Notebook 不承担：

- 项目状态
- 执行计划
- completion lane
- 收口治理
- 项目审批

### 3. 不是工作空间镜像

工作空间中的所有产物不会自动进入 Notebook。

只有用户明确指定保存的产物，才会进入 Notebook。

### 4. 不是聊天替代品

Notebook assistant 不是完整聊天替代品，也不是另一个全功能 thread。

它是围绕 Notebook 内容工作的加工助手。

## 核心对象模型

Notebook 的正式对象建议定义为：

- `InboxItem`
- `Note`
- `Asset`
- `Directory`
- `Tag`

### 1. InboxItem

`InboxItem` 不是最终内容对象，而是内容进入 Notebook 时的待整理入口状态。

它的意义是：

- 先接住内容
- 后续再整理归档

可能来源于：

- 闪记
- 聊天沉淀
- 用户手工新建的草稿
- 用户指定归档的 workspace 产物

### 2. Note

`Note` 是知识表达对象。

适合承载：

- 笔记正文
- 研究整理
- 学习记录
- 会议纪要
- 对话总结后的正式内容
- 草稿型文本

特征：

- 可编辑
- 可版本化
- 可改写
- 可总结
- 可归档

### 3. Asset

`Asset` 是材料对象。

适合承载：

- 用户明确保存进 Notebook 的工作产物副本
- html
- 图片
- 报告
- 截图
- 原始资料
- 导出文件

关键原则：

**Asset 是副本，不是 workspace 文件的外链。**

### 4. Directory

目录是 Notebook 的主组织层。

作用：

- 放置 Note
- 放置 Asset
- 帮助用户构建长期可维护的知识结构

### 5. Tag

标签是轻量分类层。

作用：

- 跨目录聚合
- 快速筛选
- 辅助整理

不承担主结构职责。

## Inbox 的定位

Notebook 首页建议采用：

**收件箱视角**

这意味着：

- 所有新进入 Notebook 的内容，默认先进收件箱
- 用户之后再整理到目录和标签体系中

这比“目录树优先”更符合真实用户习惯，也能同时接住：

- 闪记
- 聊天沉淀
- 工作产物归档

## 核心内容来源

Notebook 主要接收 4 类内容：

### 1. 用户主动书写

- 新建笔记
- 闪记
- 草稿记录

### 2. 聊天沉淀

用户可以通过快捷键或自然语言，让系统把一次聊天沉淀为笔记。

例如：

- “把这次聊天总结成一篇笔记”
- “存到某个目录”
- “重点记录某些信息”

### 3. 工作材料归档

用户可以显式指定：

- 把工作空间中某个产物保存到 Notebook
- 放到某个目录
- 作为长期保留材料

例如：

- html
- 报告
- 图片
- 导出文件

### 4. AI 再加工内容

例如：

- 从 Asset 生成 Note
- 对现有 Note 做总结、改写、扩写
- 把聊天内容清洗成结构化笔记

## 核心用户动作

Notebook 的核心用户动作建议固定为这 6 类：

### 1. 记下来

- 新建笔记
- 闪记
- 临时记录

### 2. 从聊天沉淀

- 一键保存本次聊天
- 指定目录保存
- 指定重点生成结构化笔记

### 3. 归档工作产物

- 将用户指定的 workspace 产物保存到 Notebook
- 保存为 Asset 副本

### 4. 整理归档

- 调整标题
- 调整目录
- 打标签
- 从收件箱整理为正式内容

### 5. AI 加工

- 总结
- 改写
- 扩写
- 提炼重点
- 从材料生成笔记

### 6. 找回来

- 搜索
- 最近内容
- 历史版本
- 回收站恢复

## 正式用户流程

Notebook 的标准流程建议定义成：

**输入 -> 收件箱 -> 加工整理 -> 归档 -> 检索复用**

### Flow 1：快速记录

- 用户闪记 / 新建草稿
- 内容进入收件箱

### Flow 2：聊天沉淀为笔记

- 用户通过快捷键或自然语言发起
- assistant 生成 Note 草稿
- 保存到收件箱或指定目录

### Flow 3：工作产物归档到 Notebook

- 用户选择某个 workspace 产物
- 系统复制副本到 Notebook，形成 Asset
- 保存到收件箱或指定目录

### Flow 4：从材料加工成笔记

- 用户对某个 Asset 发起总结/整理
- assistant 生成正式 Note
- 原 Asset 仍保留

### Flow 5：整理收件箱

- 用户把 InboxItem 归档到目录
- 设标题 / 标签 / 分类

### Flow 6：检索与再利用

- 搜索
- 打开
- 继续改
- 再导出 / 再整理

## Notebook assistant 的角色

Notebook assistant 的正式定位建议是：

**内容加工助手**

它负责：

- 把聊天沉淀成笔记
- 帮用户整理现有笔记
- 从材料生成笔记
- 提炼结构和重点

它不负责：

- 项目管理
- 长期记忆自动提炼
- 隐式推进其他对象
- 完整聊天替代

## 首页信息架构

Notebook 首页建议默认显示：

- 收件箱
- 最近内容
- 搜索入口
- 新建笔记 / 闪记 / 从聊天沉淀入口

目录树仍然存在，但不再是首页唯一主角。

### 首页的核心感觉

用户打开 Notebook 应该感觉：

**“这里是我所有值得留下来的内容入口。”**

而不是：

- 文件系统
- 项目面板
- agent 内部状态面

## 关键产品原则

### 原则 1

Notebook 的重要写入必须是显式的。

### 原则 2

工作空间产物进入 Notebook 时，保存的是副本，不是引用。

### 原则 3

assistant 负责加工，不负责接管用户资产。

### 原则 4

收件箱优先于结构化归档。

### 原则 5

Notebook 的主心智始终是：

**用户的知识与材料资产库。**

## 不应该再发生的偏移

后续设计中应避免再次把 Notebook 拉向：

- 项目收口流程
- 长期记忆提炼面
- 候选治理中心
- 复杂 agent orchestration 壳

如果这些能力未来仍然存在，也不应该以 Notebook 为主承载面。

## 总结

这次重新定义后，Notebook 的正式一句话定义是：

**Notebook 是 Nion 中用户拥有的个人知识与工作材料库，用于显式保存、整理、加工、检索和复用值得长期保留的内容。**

它的默认产品重心是：

**收件箱驱动的内容沉淀与整理。**

它的对象模型是：

**`InboxItem + Note + Asset + Directory + Tag`**

它的独特价值是：

**把聊天沉淀与工作材料归档，自然转化成用户自己的长期内容资产。**
