# 2026-03-30 Project 模块脑暴纪要

## 背景

本轮讨论的起点不是单纯增加一个新模式，而是思考如何把 `superpowers` 这一整套从头脑风暴、设计、计划、执行到 review 的方法论，落成 Nion 里的一个可持续成长的能力模块。

讨论后的核心判断是：

- `superpowers` 不应该只做成主助手里的一个 `mode`
- 更合适的产品形态是一级模块 `Project`
- `Project` 负责承载长期工作，而不是单轮对话增强

原因在于 `superpowers` 有明显的持续性特征：

- 要承载多轮工作推进，而不是一次性回答
- 要沉淀项目上下文、阶段结果和产物
- 要随着使用积累用户习惯、方法论与可复用 skill
- 后续还要和 OpenViking 记忆升级、hooks、自动化形成闭环

因此，`Project` 的本质应是一个长期工作的容器，而不是一个单次对话的推理模式。

## 核心定位

当前定义下：

- `Project` 是工作容器
- `Chat` 是交互入口
- `Notebook` 是用户资产
- `Memory` 是学习与沉淀层
- `Hooks / Automation` 是推进器与触发器

这几个模块之间必须明确 owner 边界，避免职责重叠。

### Project 的职责

- 管理项目目标、上下文、计划、任务、执行记录、Review 结论、产物与项目状态
- 承接 `brainstorming -> design -> planning -> implementation -> review -> delivery` 的工作流
- 为项目内聊天提供稳定的上下文范围
- 在任务结束后提供“提炼 skill / 提炼习惯 / 提炼长期记忆”的快捷入口

### Project 不负责的事情

- 不直接替代主聊天
- 不直接替代 Notebook
- 不直接等同于长期记忆系统
- 不由 hooks 定义业务模型

## Project 与 Chat 的关系

本轮已达成的共识是：

- 主聊天允许发起创建项目
- 主聊天不提供“切换项目”的入口
- 项目切换发生在 `Project` 模块内部
- 用户从项目页进入聊天后，该聊天线程与项目绑定
- 绑定后的聊天产物、引用、执行上下文都默认归属该项目

这意味着产品形态不是“项目和聊天二选一”，而是：

- 全局聊天负责发起
- 项目页负责管理
- 项目内聊天负责推进

推荐的一条基础交互链路：

1. 用户在聊天里提出一个需要长期推进的目标
2. 系统生成“创建项目”卡片，由用户确认
3. 创建完成后，用户进入项目页
4. 用户从项目页进入“项目聊天 / 开发会话”
5. 后续该会话的工作目录、产物、计划和状态都关联到该项目

## Project 的初始对象模型

当前讨论里，用户希望第一版项目属性先保持简单，但项目页展示又需要看到计划、进度和状态。

因此建议把 `存储字段` 和 `展示指标` 拆开。

### 第一版建议的基础字段

- `id`
- `name`
- `lifecycle_status`
- `workflow_phase`
- `created_at`
- `updated_at`

其中：

- `lifecycle_status` 用于表达项目是否仍然存活
  - `active`
  - `completed`
  - `archived`
  - `abandoned`
- `workflow_phase` 用于表达项目当前推进到哪一步
  - `brainstorming`
  - `design`
  - `planning`
  - `implementation`
  - `review`
  - `delivery`

这两个字段建议分开，而不是混成一个状态字段。因为“项目已完成”和“当前处于 review 阶段”是两个不同维度，混在一起后续会很难扩展。

### 第一版建议的展示指标

这些指标可以先做成派生值，不一定第一天就全部持久化：

- 计划总数
- 进行中计划数
- 已完成计划数
- 任务总数
- 进行中任务数
- 已归档任务数
- 最近活跃时间
- 关联线程数
- 产物数量
- 总体完成度

## Project 与 Notebook 的边界

本轮结论非常明确：

- 项目中的文档和产物属于项目资产
- Notebook 属于用户资产
- agent 可以辅助用户管理 Notebook
- 但 agent 不应默认替用户把项目内容写进 Notebook

推荐的关系是：

- 项目负责产出总结、复盘、方法草稿、经验草稿
- 系统在任务或项目结束后提示用户：
  - “是否沉淀为个人笔记”
  - “是否提炼为方法卡”
  - “是否提炼为经验条目”
- 只有用户确认后，内容才进入 Notebook

这样能避免 Notebook 被系统自动污染，也能保持 `Notebook 是用户资产，不是 agent memory` 这一现有边界。

## Project 与 Memory 的边界

项目会天然产生两类可沉淀的信息：

### 1. 项目内记忆

只服务当前项目，例如：

- 项目背景
- 关键决策
- 用户在该项目里的偏好
- 已验证的实现路径
- 已踩过的坑

### 2. 跨项目长期记忆

在多个项目之间复用，例如：

- 用户习惯
- 风格偏好
- 常用工作方式
- 可复用方法论
- 可以抽取为 skill 的流程模板

因此推荐的原则是：

- 项目工作过程中先进入 `Project Memory`
- 项目结束时再由用户确认，提炼少量高价值内容进入长期记忆或技能系统

这样既不会让全局记忆被项目噪声污染，也能逐步形成真正对用户有帮助的成长能力。

## Project 与 Hooks / Automation 的关系

这部分是本轮最重要的增量之一。

如果 `Project` 要支持持续自动推进，仅靠手动点下一步是不够的，它必须有事件驱动能力。也就是说：

- hooks / automation 不负责定义项目
- 但它们要负责驱动项目推进

未来可以支持的典型触发器包括：

- 任务完成后，自动评估是否启动下一任务
- review 通过后，自动进入下一个 workflow phase
- 某个产物生成成功后，自动触发验证或总结
- 某个子任务失败后，自动创建 remediation 任务
- 定时检查项目阻塞，并生成建议动作

这条链路很关键，因为它决定了 `Project` 不只是一个静态容器，而是一个可以持续运行的工作引擎。

## 当前达成的产品共识

### 已确定

- `Project` 是一级模块
- `Project` 是长期工作容器
- `Chat` 是交互入口
- 主聊天只能发起项目，不能负责项目切换
- 项目页负责项目切换、项目管理和进入项目聊天
- 项目聊天绑定项目上下文与产物范围
- Notebook 不由 agent 自动写入
- 项目结束后应提供提炼 skill / 习惯 / 长期记忆的快捷入口
- hooks / automation 是项目推进器

### 尚未完全收敛

- 项目首页的信息架构
- 项目详情页的模块分区
- 计划与任务的层级关系
- 进度如何计算
- 项目内聊天是否按“探索 / 实施 / Review”自动拆多线程
- 项目与 OpenViking 长期记忆的具体写入策略
