# Project 模块信息架构与状态机设计

## 目标

定义 Nion `Project` 模块的 v1 产品设计，重点覆盖：

- Project 详情页信息架构
- Project 的隐式阶段状态机
- `阶段 -> 实施计划 -> 内部子任务` 的对象模型
- 全局实施计划看板
- Project Chat 与普通聊天的关系
- Project 时间线与产物版本历史的关系

本设计服务于一个核心目标：

> 把 `superpowers` 从一次性对话增强能力，落成 Nion 里一个可持续推进、可沉淀、可成长的长期工作系统。

## 设计结论总览

### 1. Project 是一级模块，不是聊天模式

Project 是长期工作容器，负责承载：

- 项目目标
- 项目上下文
- 项目阶段
- 实施计划
- 执行历史
- 关键产物
- 项目内记忆

聊天只是 Project 的交互入口之一，不是 Project 的替代品。

### 2. 用户可管理的最小单位是实施计划，不是内部子任务

Project 的层级固定为：

- `阶段`
- `实施计划`
- `内部子任务`

只有前两层是用户级对象；内部子任务由 agent 在实施计划内部自行拆解和执行，不进入主界面管理模型。

### 3. 阶段切换由 agent 静默处理

Project 采用隐式阶段流转，用户不需要选择“当前用途”或手动切阶段。

系统内部阶段固定为：

- `头脑风暴`
- `设计`
- `计划`
- `实施`
- `完成`

前台只展示：

- 当前阶段
- 当前主进行实施计划
- 当前阻塞
- 下一步动作

### 4. 主历史视图是实施计划时间线，不是 Git 式提交流

Project 的主历史采用“实施计划驱动的时间线”。

产物版本历史存在，但作为计划下的附属历史，不作为 Project 主视图的第一层。

### 5. Project Chat 是独立聊天页，但继承 Project 共享上下文

Project Chat 不是内嵌在 Project 页里的聊天框，而是一个独立聊天页。

新建 Project Chat 时：

- 默认继承 Project 共享上下文包
- 不默认继承上一会话摘要
- 可通过 `@当前项目下的其他会话` 显式引入一次性快照

## 一、Project 详情页信息架构

Project 详情页的产品定位不是资料页，而是“驾驶舱”。

页面默认视觉重心放在两件事：

- `当前该做什么`
- `总体进度`

### 页面结构

建议分为 4 个主要区域：

1. 顶部总览区
2. 当前动作与阻塞区
3. 实施计划与进度区
4. 会话与时间线区

### 1) 顶部总览区

顶部总览区只回答项目最核心的全局问题：

- 项目名
- 当前阶段
- 生命周期状态
- 总体进度
- 最近活跃时间

这里的总体进度不应只显示一个孤立百分比，而应采用：

- `阶段里程碑轨道` 作为主表达
- `任务完成率/计划完成率` 作为辅助数值

建议固定展示 5 个阶段节点：

- 头脑风暴
- 设计
- 计划
- 实施
- 完成

当前阶段高亮，已完成阶段实心，未开始阶段空心。

### 2) 当前动作与阻塞区

这是 Project 详情页真正的主重心。

这一块至少包含：

- `下一步动作卡`
- `当前阻塞卡`
- `待确认事项卡`
- `当前主进行实施计划卡`

其中“下一步动作卡”是页面默认主 CTA，用来指向：

- 继续当前主会话
- 进入某个待处理实施计划
- 确认某个关口计划结果
- 处理某个阻塞

### 3) 实施计划与进度区

这里不展示内部子任务，而展示用户真正管理的实施计划。

建议包含：

- 当前阶段下的实施计划列表
- 各计划的状态
- 依赖关系摘要
- 计划完成度

默认只允许一个 `主进行实施计划`，其他实施计划可以处于：

- 候选
- 挂起
- 阻塞
- 待执行

### 4) 会话与时间线区

Project 页里不内嵌可输入的聊天框，而是提供：

- `继续当前主会话`
- `新建项目会话`
- `会话统计`
- `最近会话列表`
- `最近项目时间线`

时间线只展示项目关键事件，而不是全部底层日志。

## 二、Project 的状态模型

Project 的状态必须拆成 3 层，避免混淆：

1. Project 生命周期状态
2. Project 阶段状态
3. 实施计划状态

### 1) Project 生命周期状态

Project 生命周期只回答“这个容器现在是否仍然存活”。

建议枚举：

- `active`
- `completed`
- `archived`
- `abandoned`

说明：

- `active`：项目仍在推进或可能继续推进
- `completed`：当前项目已无待推进主线，但仍可查看历史
- `archived`：项目被归档，默认不再参与日常视图
- `abandoned`：项目被明确放弃

### 2) Project 阶段状态

Project 阶段由 agent 隐式维护，不要求用户手动切换。

建议固定为：

- `头脑风暴`
- `设计`
- `计划`
- `实施`
- `完成`

### 阶段含义

#### 头脑风暴

目标：

- 探索需求
- 澄清目标
- 收集约束
- 发散可行方向

进入信号：

- 项目刚创建
- 用户提出目标但尚未形成稳定方案

退出信号：

- 需求、目标、约束与方向已达到足够清晰度
- agent 能稳定输出结构化设计

#### 设计

目标：

- 收敛方案
- 明确结构、边界和关键决策
- 形成可以进一步计划化的设计结果

进入信号：

- 头脑风暴结果已经收敛到可设计的程度

退出信号：

- 已形成可执行设计
- 关键边界已明确
- 可以开始拆实施计划

#### 计划

目标：

- 生成实施计划
- 确立依赖关系
- 标注关口计划
- 明确执行顺序

进入信号：

- 设计结果已经足够稳定，可以拆计划

退出信号：

- 至少存在一条可执行实施计划链路
- 计划依赖关系已建立

#### 实施

目标：

- 执行实施计划
- 跟踪结果
- 处理中间阻塞
- 根据关口结果推进下一条计划或分支

进入信号：

- 已有可执行实施计划

退出信号：

- 主实施计划链路完成
- 当前没有待执行主线，只剩收尾/验证/沉淀

#### 完成

目标：

- 做收尾
- 可选 review
- 归档关键产物
- 提炼经验、习惯、skill 与长期记忆

进入信号：

- 主线实施计划已完成
- 当前工作已转向收尾与沉淀

退出信号：

- 默认无强制退出
- 若后续新增或重开实施计划，Project 可自动回退到 `计划` 或 `实施`

### 3) 实施计划状态

实施计划是用户可管理的最小执行对象。

实施计划状态不应该被简化成单一大枚举，建议拆成多维状态：

- `lifecycle_status`
- `queue_status`
- `hold_status`
- `hold_reason`

#### lifecycle_status

- `draft`
- `ready`
- `running`
- `completed`
- `failed`
- `canceled`
- `archived`

#### queue_status

- `not_queued`
- `queued`
- `dispatched`

#### hold_status

- `none`
- `paused`
- `blocked`
- `waiting_confirmation`
- `review_pending`
- `waiting_manual_start`

#### hold_reason

- `rate_limited`
- `dependency`
- `manual`
- `missing_input`
- `tool_error`
- `human_decision`

## 三、实施计划模型

### 1) 实施计划是用户可见的主执行对象

一个实施计划代表：

- 在某个阶段里的一段可解释执行策略
- 一组由 agent 内部拆分执行的细步骤
- 一条可以被确认、暂停、返工、恢复和复用的工作单元

实施计划不是原子 task，也不是完整阶段。

### 2) 一个阶段允许多个实施计划存在，但只允许一个主进行计划

V1 原则：

- 一个阶段可以存在多个实施计划
- 同一时刻只允许一个 `主进行实施计划`
- 其他计划处于候选、挂起、阻塞或待执行状态

这样可以既保留规划能力，又避免并发过多导致用户失控。

### 3) 实施计划执行方式是计划级属性

V1 不做项目级自动/手动开关，而是做**实施计划级**执行方式：

- `manual`
- `auto`

含义：

- `manual`：依赖满足后，进入待手动启动
- `auto`：依赖满足、资源可用且前序结果确认后，可自动进入执行

### 4) 实施计划支持简单依赖图

V1 支持简单依赖图，不做完全自由的工作流引擎。

每个实施计划可声明：

- `depends_on`

能力范围：

- 允许依赖多个前置实施计划
- 允许线性链路
- 允许汇聚关系

不做：

- 复杂表达式规则
- 任意脚本式流程图编排

### 5) 实施计划支持结果驱动的条件分支

V1 支持条件分支，但只做**结果驱动分支**。

一个实施计划完成后，可以产出结构化结果：

- `done`
- `done_with_followups`
- `needs_revision`
- `blocked`
- `canceled`

然后基于结果走向不同后继计划。

这类条件分支依然只发生在实施计划层，不下沉到内部子任务层。

### 6) 关口计划

并不是所有实施计划完成后都要求用户确认。

V1 将实施计划分成：

- 普通计划
- 关口计划

关口计划默认由系统按规则判定，用户可修改。

默认命中规则：

- 分支关口
- 阶段关口
- 高影响关口
- 用户手动标记关口

关口计划完成后进入：

- `pending_outcome_confirmation`

普通计划可在 agent 产出结果摘要后自动收口。

## 四、全局实施计划看板

Project 可以同时活跃多个，但执行资源是全局共享的。

因此执行层必须有一个**全局实施计划看板**，而不是每个项目各自维护一套队列。

### 1) 看板的调度单位是实施计划

不是子任务，也不是项目本身。

每张卡片至少展示：

- 所属项目
- 所属阶段
- 实施计划标题
- 当前状态
- 当前阻塞原因
- 执行方式（manual / auto）

### 2) 排序由用户决定

V1 不让系统给优先级。

规则：

- 系统负责状态正确
- 用户负责优先级顺序

因此全局看板排序以**用户手动拖拽**为准。

### 3) 建议的用户可见列

前端不直接暴露内部全部状态维度，而是映射成用户能理解的列：

- `待整理`
- `待执行`
- `执行中`
- `已暂停`
- `待评审`
- `已完成`

不同内部状态可映射到同一列，但卡片必须显示原因标签。

### 4) 限流与 429 处理

不同项目可以同时处于活跃状态，但模型或 provider 不一定支持并发执行。

V1 处理原则：

- 遇到 `429` 或并发受限时
- 实施计划不算失败
- 进入 `paused + rate_limited`
- 给用户通知和清晰原因

系统不隐式替用户自动重排优先级，只提供建议动作：

- 稍后恢复
- 改模型
- 手动调整队列

## 五、Project Chat 设计

### 1) Project Chat 是独立聊天页

Project Chat 不内嵌在详情页里，而是独立聊天页。

Project 详情页只负责：

- 继续当前主会话
- 新建项目会话
- 查看项目内会话列表

### 2) 聊天历史分类

线程模型建议增加：

- `thread_type`
- `source_type`
- `project_id`

V1 线程分类建议至少包括：

- `general`
- `project`
- `bridge`

左侧历史记录按一级分类展示：

- 普通聊天
- 项目聊天
- 桥接聊天

其中 `项目聊天` 再按 `project_name` 分组显示。

### 3) 项目详情页中的会话区

Project 页中的会话区是“会话管理区”，不是聊天面板。

建议包含：

- `继续当前主会话`
- `新建项目会话`
- `会话总数`
- `活跃会话数`
- `最近活跃时间`
- `最近会话列表`

### 4) 主会话

一个 Project 可以有很多支线会话，但建议存在一个 `主会话` 概念：

- 主会话承接当前主进行实施计划
- 支线会话用于探索、临时问题、返工讨论、review 等

Project 详情页的默认主 CTA 应该是“继续当前主会话”。

## 六、Project Chat 的上下文继承规则

### 1) 新建项目会话时默认继承 Project 共享上下文包

新建 Project Chat 时，默认注入：

- 项目名与目标
- 当前阶段
- 当前主进行实施计划
- 最近一次已确认的计划结果
- 关键产物索引
- 项目记忆摘要

### 2) 不默认继承上一会话摘要

V1 不自动继承最近一次 Project 会话的摘要。

原因：

- 同项目内可能存在探索线、支线问题、临时讨论
- 自动继承会污染新线程
- 会造成上下文爆炸

### 3) 支持 `@当前项目下的其他会话`

如果用户要显式承接某个历史会话，可在 Project Chat 中：

- `@另一个当前项目下的会话`

限制：

- 只能引用当前项目下的其他 session
- 不能跨项目引用

### 4) `@会话` 采用一次性快照语义

V1 采用一次性快照，而不是动态关联。

注入内容建议固定为：

- 会话目标
- 关键决策
- 未完成事项
- 风险/分歧
- 关键产物引用

引入后显示为“已引入会话快照卡”，允许用户移除。

## 七、Project 时间线与产物版本

### 1) 主历史视图是实施计划时间线

Project 主时间线展示的应该是工作推进事件，而不是底层文件版本事件。

关键事件包括：

- 实施计划创建
- 实施计划进入执行
- 实施计划暂停/阻塞
- 实施计划结果确认
- 后继计划触发
- 返工计划创建
- 阶段切换
- 项目完成
- 技能/记忆提炼

### 2) 产物版本历史作为附属历史

产物版本历史存在，但挂在：

- 实施计划详情
- 产物详情

它不应该抢占 Project 首页主视图。

### 3) V1 只覆盖受管产物

Project 产物分成两类：

- `受管产物`
- `引用产物`

V1 只为 `受管产物` 建版本链。

受管产物指：

- Nion 直接生成的内容
- Nion 直接改写的内容
- Nion 结构化处理过的内容

引用产物仅做：

- 可引用
- 可展示来源
- 可关联到实施计划

不承诺版本链。

### 4) 产物恢复语义

V1 恢复操作采用**追加式恢复**：

- 恢复不会覆写历史
- 恢复会生成一个新的当前版本
- 历史版本链保持完整

建议字段：

- `restored_from_version_id`
- `restore_reason`
- `actor`
- `related_plan_id`
- `created_at`

### 5) 恢复后触发返工提示

恢复某个受管产物版本后：

- 默认不总是提示返工
- 只有当该产物归属于**已完成实施计划**时
- 系统才弹轻动作卡：
  - `新建返工计划`
  - `仅恢复版本`

### 6) 返工不重开旧计划，默认新建返工计划

V1 默认保留原计划的完成记录，并新建一个返工计划。

建议关联字段：

- `rework_of_plan_id`
- `derived_from_outcome_id`

这样 Project 时间线才能完整表达：

- 原计划完成
- 结果被判定需要修订
- 某个关键产物被恢复
- 新建返工计划
- 返工计划完成

## 八、对 Git 的产品立场

Project v1 不应直接对普通用户暴露 Git 概念。

推荐立场：

- Project 对用户提供的是“时间线、版本、恢复、返工”
- 而不是“提交、分支、合并、冲突”

因此 v1 的产品定义应建立在：

- Project 时间线
- 受管产物版本
- 返工链路

而不是建立在 Git 之上。

后续若某类 Project 是代码型项目，可考虑给底层增加 Git 适配器，但不改变前台产品语言。

## 九、V1 强约束

以下内容建议在 V1 直接锁死，避免边做边漂移：

- Project 是一级模块，不是聊天模式
- 详情页是驾驶舱，不是资料页
- 阶段切换由 agent 静默处理
- 用户不管理“用途”，只看阶段和下一步动作
- 用户级最小执行对象是实施计划
- 内部子任务不进入主界面
- 实施计划支持简单依赖图和结果驱动分支
- 同一阶段可有多个实施计划，但同一时刻仅一个主进行计划
- 全局执行看板的调度单位是实施计划
- 排序由用户手动决定
- Project Chat 是独立聊天页
- 新会话默认继承 Project 共享上下文包，不默认继承上一会话摘要
- `@会话` 仅限当前项目内，且为一次性快照
- 主历史是实施计划时间线
- V1 只为受管产物做版本链
- 返工默认新建返工计划，不重开旧计划
